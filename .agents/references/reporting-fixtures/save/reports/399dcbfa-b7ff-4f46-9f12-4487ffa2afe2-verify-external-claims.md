### A002 — `std::filesystem::remove(path)` versus `remove(path, error_code&)`
- Result: VERIFIED
- Proposition: In C++23, `std::filesystem::remove(path)` throws `std::filesystem::filesystem_error` when an underlying operating-system error prevents the operation from meeting its specification, while `remove(path, std::error_code&)` reports that operating-system error through the supplied error code without throwing it.
- Applicability: `Engine/Source/File/FileManager.cpp:146-150` calls the no-`error_code` overload. The server project selects `stdcpp23` in all configurations and the installed MSVC STL is 14.51. N4950 contains the applicable C++23 filesystem error-reporting rules, and official MSVC STL 14.51 source shows the same overload split.
- Evidence: C++23 N4950 [fs.op.remove] declares `remove(const path&)` and `remove(const path&, error_code&) noexcept`, then says exceptions are governed by [fs.err.report]. [fs.err.report]/2.1 requires functions without an `error_code&` argument to throw `filesystem_error` when an underlying API error prevents the function meeting its specification. [fs.err.report]/3.1 requires functions with `error_code&` to set that argument on the corresponding underlying API error; the remove overload is also expressly `noexcept`. MSVC STL 14.51 checks the native result and calls `_Throw_fs_error` in the first overload, while the second writes `_Make_ec(_Result._Error)` into `_Ec` and is `noexcept`.
- Official source: [WG21 C++23 working draft N4950](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf), rendered [N4950 [fs.op.remove]](https://timsong-cpp.github.io/cppwp/n4950/fs.op.remove) and [N4950 [fs.err.report]](https://timsong-cpp.github.io/cppwp/n4950/fs.err.report); [Microsoft STL 14.51 `remove` overload implementations](https://github.com/microsoft/STL/blob/msvc-build-tools-14.51/stl/inc/filesystem#L3638-L3654).
- Dependent finding: Establishes the external premise required by repository-review F002/A002 and adversarial-review R001: an operating-system removal failure can escape the current `FileManager::RemoveFile` call as `filesystem_error`, whereas the error-code overload reports that failure without throwing it.
