# Network/Server/ - Server Session and Managers

## Overview

Server-side game networking (`BT_SERVER`). `ServerSession` (via `gpServerSession`) is a thin orchestrator over four domain managers — fleet, transfer, broadcaster, client — owned as `unique_ptr`s; managers reach each other through `gpServerSession`, with public data members as the cross-manager API. Fleet, client, and broadcaster process network request queues; the transfer manager instead consumes frame `transferRequests`. The fleet manager delegates flagship-direction logic and the pending-flagship-update queue to a `FleetNavigationController`. `engine::GameBase::ServerUpdate` drives the per-tick sequence (`PreTickNetwork` parse+request-drain, `PrepareTick` active-set recompute, frame tick, transfer harvest, then `BroadcastTick`); the manager methods are the steps, not a single ServerSession flow.

## Invariants

- **Parallel-vector invariant**: `ServerSession::mClientOwnedPlayerIds[iClientId]` and `ClientConnection::authorizedCoords` are index-aligned; every spawn / transfer / death / relink must mutate both in lockstep.
- **Active set**: rebuilt each tick from client subscriptions plus any coord with players plus pending destroy coords; `kOriginCoord` always included.
- **Spawn assignment by snapshot diff**: the server can't know which player entity the frame tick will mint for a `kSpawnPlayer` status change, so it snapshots origin-coord player ids pre-tick and diffs post-tick, zipping new ids to waiting clients in queue order — order-sensitive on both sides. The spawned entity gets the client GUID written into `pClientGuids` so relinking can be done from frame state alone.
- **Client-dead gating**: a client is only marked dead when all owned players are gone; clients mid-transfer (pending subscription update) are skipped to avoid false positives while a player crosses a coord boundary.
- **Fleet ownership by `ClientGuid`**: fleets are keyed by persistent GUID so they survive disconnect/reconnect; a separate reap pass handles AI-managed disconnected fleets.
- **Fleet RNG lifecycle**: the fleet manager's `RandomEngine` is `TimeSeed()`ed once at construction and never re-seeded — not on session reset, quickload, or replay-load; save/load round-trips its state at the tail of the fleet block. Fleet creation draws exactly two 64-bit values to mint the persistent fleet identifier; changing that draw count breaks save/replay determinism.
- **Flagship timer (post-arrival countdown)**: `Fleet::fFrameChangeTimer` drains only while `flagship.coord == fleet.wantedCoord` — paused during transit, so cycle time is transit + `fNavigationDelay` (delay = idle time at each destination). Cardinal mode is deliberately not gated on the drain: a flagship arriving mid-cardinal keeps draining, so the timer fires the moment nav mode leaves cardinal (the un-freeze property). Fire preconditions (timer ≤ 0, coord still matches, frame loaded, not cardinal) are re-checked at fire time because a cardinal eject between ticks can move the flagship. Direction changes emit as `kUpdateFleet` status changes via the delayed StatusChange activation pattern (see [Frame/CLAUDE.md](../../Frame/CLAUDE.md)).
- **Tick-rate state in `BuildFrameInputs`**: runs every `ServerUpdate` (inside `PrepareActiveSet`), even paused — but the per-tick loop consuming `mFrameInputs[*].statusChanges` does not, and the next call wipes the map. Any sim-time progression here must advance by `gpGame->mfLastDeltaTime` (= `iFullTicks * kfDeltaTime`: zero during pause, scaled with `mTimeStep`), never `kfDeltaTime`. `TickFleetTimers` is the canonical example.
- **Transfer liveness gate**: `HarvestTransfers` drops non-player transfers whose destination has no committed player and no subscriber (`IsDestinationLive`) — prevents ghost entities accumulating in cells no client observes. `kTransferPlayer` is always allowed: the player's arrival is the subscription. The check deliberately ignores `mActiveCoords` because `kOriginCoord` is force-added every tick as a spawn bootstrap. Destinations must be Chebyshev-adjacent (distance ≤ 1); larger deltas `DEBUG_BREAK` as upstream teleport bugs.
- **Post-transfer CRC recompute**: the frame tick computes `sharedCrc` before transfers land, so `HarvestTransfers` re-runs `Frame::Crcs()` on every destination frame and logs pre/post CRCs — clients validate against `GridUpdateData.sharedCrc`, so skipping this desyncs every transfer.
- **Reconnect / load relink**: both relink paths sort GUID matches by global ID to preserve creation order before rebuilding the parallel vectors — reconnect (`TryRelinkNewClient`) and the load path (`TryRelinkClientForLoad`) — so the client-visible assign/spawn send order is creation-order stable across both reconnect and save→load. On load, the client/transfer/broadcaster managers get `ResetState()` but the fleet manager only `ClearPendingRequests()` — `ReadFleetData` + `OnResetForLoad` just restored its state, and the pending flagship updates restoration re-queued must not be cleared again.
- **Allocation suppression**: public manager entry points that grow SOA buffers or member containers wrap their body in `ScopedSuppressAllocationTracking`. These inner guards are **deliberately kept even when redundant** under an orchestrator blanket guard (`PreTickNetwork`/`BroadcastTick`/`BuildFrameInputs`/`PrepareTick` cover most entry points): recursive-mutex-style, a nested guard costs nothing under the thread-local *counter* semantics but keeps the method protected if a future caller ever invokes it outside a blanket guard — the safety is owned by the method, not borrowed from its current callers. The guard follows the *allocator*, not the call site, so an entry point that grows nothing carries none (`ServerFleetManager::ProcessDeleteFleetRequests` is the canonical exception — no allocator, no guard). Conversely `ServerSession::ComputeActiveSet` and `SendResends` are not merely redundant: they have genuinely unguarded call paths (`PrepareActiveSet`/quickload, and the per-tick resend step), so their inner guards are load-bearing. Entry points whose per-tick scratch was migrated to the workbuffer intentionally omit the guard so the tracker stays armed for them (`BroadcastStatusChanges` is the canonical example). When such an armed-by-design callee runs inside a caller that holds a blanket guard, the caller must re-arm it with a `ScopedResumeAllocationTracking` scope around the call — omitting the callee's own guard is not enough, since suppression is a thread-local *counter* (an enclosing guard keeps it positive). `ServerSession::BroadcastTick` does this around `BroadcastStatusChanges`. Fleet-sync sends (`SendFleetSyncToClient` → `game::SendFleetSync`) are workbuffer-based and ship via `NetworkManager::SendPacket` (which self-suppresses ENet's only allocation), so they cause no tracker-visible heap allocation and are intentionally *not* independently armed — they already run under the request-drain (`PreTickNetwork`), load-path (`ResetClientsForLoad`), and broadcast (`BroadcastTick`) blanket guards. `OnPlayerDeath` and `UpdateFleetNavigationDelay` likewise call the send with no inner guard for the same reason.

## Notes

- Packet parsing queues game requests into per-manager request structs — game state is never mutated mid-parse; debug-control packets and fleet navigation-delay updates act immediately. Queues are cleared at the start of each tick and drained in fixed order; requests for vanished clients are silently dropped.
- Timespeed broadcast is edge-triggered (`BroadcastTimespeedIfChanged`); newly-handshaken clients are caught up via a direct send from engine `Server::ClientHello`.
- Disconnect clears `kPaused` and restores `mTimeStep` to 1/1 once no clients remain.
