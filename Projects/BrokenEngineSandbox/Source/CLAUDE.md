# BrokenEngineSandbox - Sample Game Implementation

See also: [Game Reconciliation](../../../Documents/Architecture/GameReconciliation.md)

A space combat game demonstrating the full capabilities of the Broken Engine. Features fast-paced dogfighting, wave-based enemy spawning, and terrain interaction.

## IMPORTANT: Frame Purity Constraint

Frame code is purely functional. Frame updates must only rely on explicit function parameters -- Frame code must NEVER query Game (`gpGame`) for anything. The Frame does not know which Player is human and which is AI. Human player identity, camera shake, death screen transitions, and respawn orchestration are Game-level responsibilities. Frame code operates on data-driven parameters only (e.g., iterating all players to find alive ones, rather than querying Game for a player index).

## Engine Integration

The game follows the standard engine architecture:
- **Game class** - Inherits from `engine::GameBase`, coordinates all subsystems
- **Frame system** - Game state management, inherits from `engine::FrameBase`
- **Namespace** - All game code is in the `game` namespace
- **Data Pipeline** - Assets processed by DataPacker and loaded via FileManager

## Game Class (`Game.h/cpp`)

Central game coordinator inheriting from `engine::GameBase`. Accessed via `gpGame` singleton pointer.

**Game Lifecycle**: Manages state transitions between main menu, gameplay, and death screen via `GameFlags`. Supports new game and restart. Handles music playlist switching between menu and gameplay modes with callback-driven track progression (client-only via `#ifdef BT_CLIENT`). Camera ownership is client-only; server builds omit the Camera member entirely. Server builds (`BT_SERVER`) start directly in game mode (`kGame`) with `kNone` UI state, bypassing the main menu. `UiState::kModal` displays a modal error dialog (via `ModalScreen`) with a message stored in `mModalMessage`; `ProcessMenuInput()` blocks all input during the modal state, and the modal's OK button transitions back to `kPause`.

**Client Networking** (`#ifdef BT_CLIENT`): Integrates with NetworkClient for multiplayer using a rollback-and-replay reconciliation architecture with server-input extrapolation (not client-side prediction) and client-driven coord subscriptions. `ConnectToServer()`/`DisconnectFromServer()` manage the NetworkClient lifetime and clear all server state (per-coord reconcile states, confirmed human state, desync debug state, transfer changes, subscription queue, latest server frame) on disconnect. `StartServerDiscovery()` creates a `NetworkDiscoveryScanner` for LAN server auto-detection (covers both localhost and LAN); `PollNetworkClient()` is called between physics and render (after `UpdateFrames()`, before `Render()`) so the async reconcile worker gets the freshest network data and latest extrapolated snapshots. It polls the scanner and auto-connects when a server is found (transitioning to game mode), or triggers a `DEBUG_BREAK` and cleans up on timeout. `PollNetworkClient()` gates on `IsConnectionAccepted()` after polling ENet: if the server's connection response hasn't arrived yet, it early-returns (the main menu shows "CONNECTING..." during this period); on rejection, it populates `mModalMessage` with the server's rejection reason, disconnects, and transitions to `UiState::kModal`; on disconnection before acceptance, it shows a generic "Connection failed" modal. Once accepted, it transitions to game mode and starts gameplay music. `PollNetworkClient()` also detects server-initiated disconnects via `WasDisconnected()` and returns to the main menu (transitioning to modal if a message is set, otherwise to pause UI state). After those checks, it iterates all received player assignments via `DrainReceivedAssignments()` (updating human tracking state for each and triggering `UpdateSubscriptions()` for the new grid position), applies received full states, calls `UpdateSubscriptions()` to immediately detect and unsubscribe orphaned subscriptions, and buffers received delta updates into per-coord reconcile states. `ApplyReceivedFullStates()` has two distinct paths: on initial connection (no confirmed state for the coord), it moves the received frame directly into `mCurrentFrames`, ensures the next frame exists, hydrates client-only objects (`HydrateClientObjects()`), establishes the coord's confirmed state and sets the frame counter; on subsequent full states (confirmed state already exists for the coord), it stores the serialized frame as a pending full state in the coord's reconcile state for deferred injection during reconciliation. After processing full states, calls `TrySubscribeNext()` to advance sequential subscription. `ApplyReceivedUpdates()` iterates per-slot received updates from the NetworkClient, routes each slot's updates to the corresponding coord's `CoordReconcileState` (skipping frames at or before the coord's confirmed frame, keeping the first-received version per frame, capping per-coord `serverUpdates` map growth at `kiMaxBufferedFrames`), and tracks `miLatestServerFrame` (the highest frame number seen from the server) for clock correction. `SendNetworkInput()` sends the locally captured `mLocalPlayerInput` to the server as soon as connected (even before player assignment). `ChangeFrame()` resets the discovery scanner before disconnecting.

**Rollback and Replay** (`WaitForReconcile()`/`TryKickReconcile()`): The reconciliation timing is split across the main loop: `WaitForReconcile()` is called before physics to wait for and apply the async reconcile result (via `ApplyReconcileResult()`), and `TryKickReconcile()` is called between physics and render (alongside `PollNetworkClient()`) to kick the next reconciliation via `KickReconcile()`, so the async worker operates on the freshest network data and latest extrapolated snapshots. When `kbEnableReconcileThread` is enabled, reconciliation runs on a dedicated `PersistentWorker` thread, with `ReconcileContext` shuttling data between the main thread and the worker. Reconciliation is per-coord: `KickReconcile()` populates a `CoordReconcileWork` item for each coord in `mCoordReconcileStates` that has a valid confirmed frame, moving server updates, extrapolated snapshots, last server player inputs, and pending full states into the work item (clearing the source). Both the destructor and `DisconnectFromServer()` wait for any in-flight reconcile before teardown. The core replay logic lives in the static `Reconcile()` method (callable from either the main thread or worker thread), supported by static helpers `ReconcileEnsureNextFrames()`, `ReconcileBuildFrameInput()`, `ReconcileRunPhysics()`, `ReconcileHarvestTransfers()`, `ReconcileComputeActiveCoords()`, `ReconcileInjectPendingFullState()`, and `ReconcilePruneInactiveFrames()` that operate on `ReconcileContext` instead of Game members. Per-coord CRC fast-path: for each coord work item, checks ALL consecutive buffered server updates against per-frame `CoordExtrapolatedSnapshot` CRCs stored during physics extrapolation via `StoreExtrapolatedSnapshot(iFrame)`. Each snapshot captures the coord's CRC and serialized frame at the end of each extrapolated physics frame. If all coords pass CRC fast-path or have no changes, `Reconcile` advances `fCurrentTime` in the confirmed human state by the number of newly confirmed frames (preserving simulation time continuity) and returns early with `bCrcFastPathHandledAll`. Otherwise, proceeds to unified rollback: restores all coord frames from their confirmed serialized state into `ctx.currentFrames`, sets human tracking state from `confirmedHumanState`, injects any pending full states at or before the rollback frame via `ReconcileInjectPendingFullState()` into `currentFrames`, then replays consecutive server updates by re-running the full frame update pipeline (Interpolate, PostRender, collision, transfer, destroy, spawn) per frame. During replay, `ReconcileBuildFrameInput()` constructs per-coordinate FrameInputs from per-coord server updates, separating transfer StatusChanges into `serverTransferStatusChanges` and applying server player inputs; coords without server data for a given frame use extrapolated inputs from `lastServerPlayerInputs`. Injects matching pending full states via `ReconcileInjectPendingFullState()` into `currentFrames` at the matching frame to synchronize new cell data with the replay timeline. After each replayed frame, validates CRCs per coord against server-reported values; on mismatch, stores desync info (frame, coord, CRCs, deep-copied client Frame) into `ReconcileContext` for the main thread to handle. Replay is capped at half the available consecutive frames per reconciliation tick. `ApplyReconcileResult()` detects desyncs, sends a desync report and debug frame request to the server, activates `SetDesyncDebugMode(true)` on the NetworkClient, and enters `DesyncDebugState`. While in desync debug state: `PollNetworkClient()` early-returns after checking for the debug frame response, and Main.cpp's main loop skips reconciliation, physics, input sending, and audio. When the debug frame arrives, `CompareWithServerFrame()` calls `ServerCompare()` for per-field comparison to pinpoint exact differing fields, then disconnects with a modal message. After replay, prunes non-active coords via `ReconcilePruneInactiveFrames()`, saves confirmed state per coord (frame number and serialized frame), then performs predictive catch-up simulating with extrapolated inputs up to the main thread's current frame counter (`iTargetFrame`), storing `CoordExtrapolatedSnapshot` per coord per frame for CRC fast-path on subsequent ticks. `ApplyReconcileResult()` writes back per-coord results (new confirmed frame, serialized state, last server inputs, extrapolated snapshots) into `mCoordReconcileStates`, moves caught-up frames into `mCurrentFrames`, and updates the confirmed human state. The `CoordReconcileState` struct stores per-coord confirmed frame, serialized frame, server update buffer, extrapolated snapshots, last server player inputs, an optional pending full state, and a `uiGeneration` counter that prevents stale reconcile results from writing back to a coord that was unsubscribed and resubscribed while the reconcile was in flight. Each `CoordReconcileWork` item carries the generation from the state at kick time; `ApplyReconcileResult()` skips write-back if the generation no longer matches (indicating the coord was recycled). The `ConfirmedHumanState` struct stores global human tracking state (grid coord, player ID, armor, simulation time).

**Soft Clock Correction** (`ComputeClockCorrectionNs()`): Called from Main.cpp after reconciliation to adjust the client's physics tick rate, keeping it slightly behind the server so server updates arrive before the client simulates those frames. Computes a target offset of `ceil(RTT/2 / frameTime) + 1` frames behind the server using `miLatestServerFrame` (tracked by `ApplyReceivedUpdates()`). The error (difference between current offset and target) drives a proportional correction clamped to +/-4 steps, each step being 1/64th of a frame's duration, applied to `mUpdateRemainderNs`. The clock error is also exposed so Main.cpp can reduce the frame deficit by the error before compensation, ensuring rollbacks help the correction converge rather than fighting it. This allows the CRC fast-path in `Reconcile()` to succeed routinely, eliminating constant rollback-and-replay. Returns 0ns if no server frames have been received yet. Feeds offset, target, and error values into `ProfileManagerBase::SetClockCorrection()` for smoothed display on the network profile screen.

In network mode, `BuildFrameInputs` uses a separate code path that applies last server-confirmed player inputs from per-coord `CoordReconcileState::lastServerPlayerInputs` (extrapolation) via the `CopyPlayerInputs()` static helper (which performs min-count clamped copy to handle player count mismatches between source and destination) rather than injecting local raw input into physics frames. `CaptureLocalInput()` samples the current raw input state into `mLocalPlayerInput` for `SendNetworkInput()`, called from Main.cpp before physics/rendering to minimize input-to-send latency. When `kbEnableAutoInput` is enabled, routes through PlayerAi instead of raw input. This bypasses the offline `BuildFrameInput` helper and AI wingmen logic.

**Server Networking Orchestration** (`#ifdef BT_SERVER`): Nine server methods integrate with NetworkServer to manage multiplayer: `HandleDisconnectsServer()` drains pending disconnects from NetworkServer, converts them into `PendingPlayerDestroy` entries (capturing the player ID and grid coordinate), and removes any matching clients from the spawn queue; `HandleNewClientsServer()` queues unassigned clients for spawn; `ProcessSpawnRequestsServer()` converts network spawn/respawn requests; `ComputeActiveSetServer()` unions all clients' subscribed coordinates (iterating each client's `coordSubscriptions` slots), and also ensures destroy coordinates are in the active set so the destroy StatusChange is processed and broadcast even if no other client is nearby; `BuildFrameInputsServer()` maps network inputs to human player indices (held state, move, and direction from the latest input; pressed flags OR-merged across all inputs per tick to prevent lost button presses when multiple packets arrive per physics frame) and saves spawn StatusChanges into `mBroadcastSpawns` (transfers handled separately in `HarvestTransfersServer()`), injects `kDestroyPlayer` StatusChanges from `mPendingPlayerDestroys` into the appropriate coordinate's FrameInput (packing the player ID into the position vector), and clears `mBroadcastSpawns` at the start of each call to prevent stale data from prior physics frames; `HarvestTransfersServer()` tracks cross-cell entity transfers into `mBroadcastTransfers` and queues subscription updates with the transferred player's newly-spawned ID in the destination cell; `FinalizeNewClientsServer()` assigns spawned players to clients via `SendAssignPlayer()` (the client handles subscriptions, no full state sent here), diffs post-spawn player IDs against a pre-spawn snapshot, and calls `RefreshPreSpawnSnapshot()` to update the snapshot for subsequent physics frames in the same tick; `HandleSubscriptionUpdatesServer()` drains `PendingNewSubscription` entries from NetworkServer, validates each slot is still active and matches the expected coord on the client before sending full state via `SendCoordFullState()` (guarding against races where the client unsubscribes before the server processes the pending subscription), then sends player assignment (with the new player ID from the destination cell) via `SendAssignPlayer()` after grid transfers (the client handles subscription changes upon receiving the assignment); `BroadcastStatusChangesServer()` buffers unfiltered data (spawns, transfers, and player inputs from `mFrameInputs`) to per-coord ring buffers via `BufferFrame()`, buffers full serialized frame snapshots via `BufferFullFrame()` for debug frame request responses, then calls `SendUpdate()` per client (which iterates each client's subscription slots internally) followed by `SendResends()` which sends separate unreliable packets per slot for any unacknowledged frames. The pre-physics methods (poll/disconnect/handle/spawn) are called from Main.cpp's server loop, while the post-physics methods (finalize/subscribe/broadcast) are called per-physics-frame inside `UpdateFrames()` to ensure clients receive updates for every simulated frame.

**Human Player Tracking**: Identifies the human player by stable `player_t` ID rather than array index (indices shift due to swap-and-pop removal). Detects human death to trigger the death screen and monitors armor changes for camera shake. Tracks the human's grid coordinate across multi-frame transfers.

**Multi-Frame Grid Orchestration**: Manages the active set of grid coordinates and builds per-coordinate `FrameInput`. In client builds, the active set during gameplay is the human's cell plus neighbors (with origin always active); during the main menu, only the human's cell ({0,0}) is active (no neighbor frames are created). `BuildFrameInputs` maps human input to the human's cell and drives AI wingmen via `PlayerAi`. In server builds, only human players exist -- `ComputeActiveSetServer()` computes the active set as the union of all connected clients' subscribed coordinates (iterating each client's slot-based `coordSubscriptions`), and `BuildFrameInputsServer()` maps each client's network input to their human player's index via `NetworkServer::DrainPendingInputs()` and buffers StatusChanges for broadcasting. Creates frames at missing coordinates, ensures destination frames exist for buffer swaps, and garbage-collects frames outside the active set.

**Client-Driven Coord Subscriptions** (`UpdateSubscriptions()`/`TrySubscribeNext()`): The client manages which grid coordinates it subscribes to, replacing server-computed active sets. `UpdateSubscriptions()` computes the desired coords in priority order (human's cell first, then direct neighbors, then origin if not already included), sends `SendUnsubscribe()` for slots whose coords are no longer desired, builds a subscription queue of desired coords not yet subscribed, and calls `TrySubscribeNext()` to begin subscribing. `TrySubscribeNext()` subscribes one coord at a time (sequential subscription): if any slot is in kSubscribing or kWaitingFullState state, it waits for that subscription to complete before sending the next `SendSubscribe()`. Each full state reception in `ApplyReceivedFullStates()` calls `TrySubscribeNext()` to advance to the next coord in the queue. This sequential approach prevents overwhelming the server with simultaneous full state sends during grid transitions.

**Transfer Harvesting**: After carry-forward, reads transfer requests from active frames and spawns entities into destination cells via a centralized `SpawnTransfer()` helper. In client builds, `HarvestTransfers()` uses two distinct paths: during reconciliation (when server transfer data is available in `mServerTransferStatusChanges`), it sorts transfers by `uiSequence` to restore original spawn order (which is lost during network serialization's type-grouping), then applies all transfers from the server via `ApplyServerTransfers()` and tracks human player grid migration from local `transferRequests` without spawning (the server already spawned entities), identifying the human's new player ID in the destination cell by position-matching against recently-spawned players (falling back to the last player if no match is found); during extrapolation or offline play, it performs local transfer harvesting from `transferRequests`, records transfers into the human's cell for replay determinism via `mPendingTransferChanges`, and tracks human player grid coordinate migration. The static `ReconcileHarvestTransfers()` mirrors this two-path logic for the reconcile worker thread: it uses server transfers when available (during server-validated replay) via the same `ApplyServerTransfers()` helper, and falls back to local transfer harvesting with entity spawning during catch-up and gap replay phases. `ApplyServerTransfers()` is a static helper that deduplicates the shared server-transfer application logic between `HarvestTransfers()` and `ReconcileHarvestTransfers()`, sorting by sequence and spawning transfer entities into destination frames. In server builds, `HarvestTransfersServer()` assigns sequential `uiSequence` numbers to each coordinate's transfers for deterministic ordering across the network, records transfers into `mBroadcastTransfers`, and detects human player grid transfers across all connected clients, capturing the newly-spawned player ID from the destination cell and queuing `SubscriptionUpdate` entries for `HandleSubscriptionUpdatesServer()` to send player assignment (with the new ID) and full-state updates for newly-visible cells. During replay playback, skips human-cell transfers (handled by `ApplyTransferStatusChanges()` which processes transfer entries from the recorded stream and removes them before checksum validation).

**Spawn Orchestration**: In client builds, buffers spawn and respawn status changes that are drained by GameBase only when physics steps will run, preventing event loss on frames with zero full updates. Uses `SpawnFlags_t` (flags-based via `common::Flags<SpawnFlags>`) to track waiting-for-human-spawn and respawn-requested states. On respawn, resets the human's grid coordinate to origin. In server builds, `ProcessSpawnRequestsServer()` converts network spawn/respawn requests into `ClientSpawnInfo` entries, `BuildFrameInputsServer()` injects spawn StatusChanges for waiting clients and calls `RefreshPreSpawnSnapshot()` to capture player IDs at the spawn coordinate, and `FinalizeNewClientsServer()` matches newly-spawned players to waiting clients by diffing post-spawn IDs against the snapshot, then sends player assignment via `SendAssignPlayer()` (the client handles subscriptions and full state requests), and calls `RefreshPreSpawnSnapshot()` again so subsequent physics frames in the same tick can correctly diff new spawns. `HandleNewClientsServer()` queues clients without assigned players for initial spawn. `Reset()` consolidates all human tracking state cleanup (player ID, spawn flags, armor, grid coordinate, pending changes).

**Persistence**: Quicksave via grid serialization (all frames plus human grid coordinate). Sound settings persisted separately. `ReplayMeta` struct captures human tracking state (grid coordinate, player ID, armor) and is persisted to a separate `.replay.meta` file for deterministic replay restore via `RestoreReplayMeta()`.

**PlayerAi** (`PlayerAi.h/cpp`): Drives AI wingmen with gradient-based terrain contour following and targeted burst fire. Includes edge-crossing encouragement: a 10-second cooldown timer per player that, when expired, checks proximity to frame edges and steers toward the nearest one to encourage grid-cell transfers (cooldown initialized to 10s on vector grow so freshly-spawned/transferred players don't immediately seek edges). Client-only; called per AI player during `BuildFrameInput()`, and also used for the human player when `kbEnableAutoInput` is enabled. Server builds have no AI wingmen -- only human players exist in multiplayer.

## Configuration Files

| File | Purpose |
|------|---------|
| `Pch.h` | Compile-time feature toggles: vcxproj defines either `BT_CLIENT` or `BT_SERVER` explicitly. `kbSingleInstance` is true for server builds. `kpcBuildConfigName` identifies the build configuration (Debug/Profile/Release) for client-server compatibility validation during the connection handshake. `kbEnableAutoInput` routes the human player through PlayerAi instead of raw input for automated testing (debug only); the server sees regular PlayerInput and doesn't know it's AI-generated. `kbEnableReconcileThread` controls whether reconciliation runs on a dedicated thread (currently enabled). `kbEnableNetworkSimulation` enables simulated packet loss and variable latency on network receive paths (debug only; false in Profile and Release). `inline constexpr bool` toggles with `if constexpr` for zero-overhead conditional compilation. Includes `Common.h` and `Engine.h` aggregation headers |
| `Frame/HealthDamage.h` | Combat balance values and collision category/mask configuration |
| `Profile/GameProfile.h` | Performance profiling zones |
| `Version.h` | Save file version tracking |

## Build Configuration

The vcxproj uses `/fp:strict` for deterministic floating-point math across different hardware configurations, complementing the engine's SSE4-only DirectXMath configuration and FMA3 disable.
