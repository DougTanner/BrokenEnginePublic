# BrokenEngineSandbox - Sample Game Implementation

See also: [Game Reconciliation](../../../Documents/Architecture/GameReconciliation.md)

A space combat game demonstrating the full capabilities of the Broken Engine. Features fast-paced dogfighting, wave-based enemy spawning, and terrain interaction.

## IMPORTANT: Frame Purity Constraint

Frame code is purely functional. Frame updates must only rely on explicit function parameters -- Frame code must NEVER query Game (`gpGame`) for anything. The Frame does not know which Player is human and which is AI. Human player identity, camera shake, death screen transitions, and respawn orchestration are Game-level responsibilities. Frame code operates on data-driven parameters only (e.g., iterating all players to find alive ones, rather than querying Game for a player index).

## Engine Integration

The game follows the standard engine architecture:
- **Game class** - Inherits from `engine::GameBase`, coordinates all subsystems
- **Frame system** - Game state management, inherits from `engine::FrameBase`
- **Namespace** - All game code is in the `game` namespace
- **Data Pipeline** - Assets processed by DataPacker and loaded via FileManager

## Game Class (`Game.h` + `Game.cpp`, `GameClient.cpp`, `GameClientReconcile.cpp`, `GameClientReconcileReplay.cpp`, `GameServer.cpp`)

Central game coordinator inheriting from `engine::GameBase`. Accessed via `gpGame` singleton pointer. The implementation is split across five .cpp files: `Game.cpp` (core/shared logic), `GameClient.cpp` (client networking and subscription management), `GameClientReconcile.cpp` (main thread interface, CRC fast-path, and reconciliation orchestrator), `GameClientReconcileReplay.cpp` (replay pipeline helpers), and `GameServer.cpp` (server networking orchestration). `SpawnTransfer()` is a `game` namespace free function declared in `Game.h` and defined in `Game.cpp` that spawns transferred entities (spaceships, blasters, missiles, players) into a destination frame based on `StatusChangeType`.

**Game Lifecycle**: Manages state transitions between main menu, gameplay, and death screen via `GameFlags`. Handles music playlist switching between menu and gameplay modes with callback-driven track progression (client-only via `#ifdef BT_CLIENT`). Camera ownership is client-only; server builds omit the Camera member entirely. Server builds (`BT_SERVER`) start directly in game mode (`kGame`) with `kNone` UI state, bypassing the main menu. `UiState::kModal` displays a modal error dialog (via `ModalScreen`) with a message stored in `mModalMessage`; `ProcessMenuInput()` blocks all input during the modal state, and the modal's OK button transitions back to `kPause`.

**Client Networking** (`GameClient.cpp`, `#ifdef BT_CLIENT`): Integrates with NetworkClient for multiplayer using a rollback-and-replay reconciliation architecture with server-input extrapolation (not client-side prediction) and client-driven coord subscriptions. `ConnectToServer()`/`DisconnectFromServer()` manage the NetworkClient lifetime and clear all server state (per-coord reconcile states, confirmed human state, desync debug state, transfer changes, subscription queue, latest server frame) on disconnect. `StartServerDiscovery()` creates a `NetworkDiscoveryScanner` for LAN server auto-detection (covers both localhost and LAN); `PollNetworkClient()` is called between physics and render (after `UpdateFrames()`, before `Render()`) so the async reconcile worker gets the freshest network data and latest extrapolated snapshots. It polls the scanner and auto-connects when a server is found (transitioning to game mode), or triggers a `DEBUG_BREAK` and cleans up on timeout. `PollNetworkClient()` gates on `IsConnectionAccepted()` after polling ENet: if the server's connection response hasn't arrived yet, it early-returns (the main menu shows "CONNECTING..." during this period); on rejection, it populates `mModalMessage` with the server's rejection reason, disconnects, and transitions to `UiState::kModal`; on disconnection before acceptance, it shows a generic "Connection failed" modal. Once accepted, it transitions to game mode and starts gameplay music. `PollNetworkClient()` also detects server-initiated disconnects via `WasDisconnected()` and returns to the main menu (transitioning to modal if a message is set, otherwise to pause UI state). After those checks, it processes server-authoritative player state notifications via `DrainReceivedPlayerStates()` (handling kSpawned and kChangedFrame by updating `mHumanGridCoord`, and kDied by triggering the death screen when the human player's ID matches), iterates all received player assignments via `DrainReceivedAssignments()` (updating human tracking state for each and triggering `UpdateSubscriptions()` for the new grid position), applies received full states, calls `UpdateSubscriptions()` to immediately detect and unsubscribe orphaned subscriptions, and buffers received delta updates into per-coord reconcile states. `ApplyReceivedFullStates()` has two distinct paths: on initial connection (no confirmed state for the coord), it moves the received frame directly into `mCurrentFrames`, ensures the next frame exists, hydrates client-only objects (`ClientInitAll()`), establishes the coord's confirmed state and sets the frame counter; on subsequent full states (confirmed state already exists for the coord), it stores the serialized frame as a pending full state in the coord's reconcile state for deferred injection during reconciliation. The confirmed human state's `fCurrentTime` is only set from the first coord's full state (when still zero); subsequent coords arrive at higher frame numbers and would desync the confirmed time vs. `iMinConfirmedFrame` during reconciliation rollback. After processing full states, calls `TrySubscribeNext()` to advance sequential subscription and sets `mbReconcileHasNewData` to signal that reconciliation should run. `ApplyReceivedUpdates()` iterates per-slot received updates from the NetworkClient, routes each slot's updates to the corresponding coord's `CoordReconcileState` (skipping frames at or before the coord's confirmed frame, keeping the first-received version per frame, capping per-coord `serverUpdates` map growth at `kiMaxBufferedFrames`), tracks `miLatestServerFrame` (the highest frame number seen from the server) for clock correction, and sets `mbReconcileHasNewData` to signal that reconciliation should run. `ChangeFrame()` resets the discovery scanner before disconnecting. Network logging is limited to one-time events (connection, disconnection, rejection messages) rather than per-frame updates.

**Rollback and Replay** (`GameClientReconcile.cpp`, `WaitForReconcile()`/`TryKickReconcile()`): The reconciliation timing is split across the main loop: `WaitForReconcile()` is called before physics to wait for and apply the async reconcile result (via `ApplyReconcileResult()`), and `TryKickReconcile()` is called between physics and render (alongside `PollNetworkClient()`) to kick the next reconciliation via `KickReconcile()`, so the async worker operates on the freshest network data and latest extrapolated snapshots. `TryKickReconcile()` early-returns when `mbReconcileHasNewData` is false, preventing reconciliation from running every tick when no new server data has arrived; the flag is cleared after kicking. When `kbEnableReconcileThread` is enabled, reconciliation runs on a dedicated `PersistentWorker` thread, with `ReconcileContext` shuttling data between the main thread and the worker. Reconciliation is per-coord: `KickReconcile()` populates a `CoordReconcileWork` item for each coord in `mCoordReconcileStates` that has a valid confirmed frame, moving server updates, extrapolated snapshots, and pending full states into the work item (clearing the source). Both the destructor and `DisconnectFromServer()` wait for any in-flight reconcile before teardown. The core replay logic lives in the static `Reconcile()` method (callable from either the main thread or worker thread), which is a short orchestrator that delegates to five phase methods: `ReconcileCrcFastPath()` (CRC fast-path check and early return), `ReconcileRollback()` (restore confirmed state), `ReconcileFindReplayRange()` (determine consecutive server data range), `ReconcileReplay()` (replay with server updates and CRC validation), and `ReconcileCatchUp()` (predictive catch-up to current frame). These are supported by additional static helpers `ReconcileEnsureNextFrames()`, `ReconcileBuildFrameInput()`, `ReconcileRunTick()` (which calls `game::RunFrameTick()` from `FrameTick.h` to share the same unified physics code path as GameBase's main update loop), `ReconcileComputeActiveCoords()`, `ReconcileInjectPendingFullState()`, and `ReconcilePruneInactiveFrames()`. All static helpers operate on `ReconcileContext` instead of Game members. Per-coord CRC fast-path: for each coord work item, checks ALL consecutive buffered server updates against per-frame `CoordExtrapolatedSnapshot` CRCs stored during physics extrapolation via `StoreExtrapolatedSnapshot(iFrame)`. Each snapshot captures the coord's CRC, input CRC, and serialized frame at the end of each extrapolated physics frame. The CRC matching loop bounds at `iTargetFrame` to prevent checking beyond frames the client has simulated; a missing snapshot within range is a real failure. Gapped coords (where the first server update is beyond `confirmed+1`, indicating missing intermediate frames) are skipped with `continue` rather than failing the fast-path, preserving their updates for when the gap is filled by resends; this prevents gapped coords from forcing the expensive full reconcile path. If all coords pass CRC fast-path, are skipped due to gaps, or have no changes, `Reconcile` advances `fCurrentTime` in the confirmed human state by the difference between the new minimum confirmed frame (tracked across all coords' latest matched frames) and the old minimum confirmed frame (preserving simulation time continuity) and returns early with `bCrcFastPathHandledAll`. Otherwise, proceeds to unified rollback: restores all coord frames from their confirmed serialized state into `ctx.currentFrames`, sets human tracking state from `confirmedHumanState`, reads `fCurrentTime` from the deserialized frame at `iMinConfirmedFrame` (since `confirmedHumanState.fCurrentTime` may not match when coords were confirmed at different frame numbers), injects any pending full states at or before the rollback frame via `ReconcileInjectPendingFullState()` into `currentFrames`, then replays consecutive server updates by re-running the full frame update pipeline (Interpolate, PostRender, collision, transfer, destroy, spawn) per frame. During replay, `ReconcileBuildFrameInput()` constructs per-coordinate FrameInputs from per-coord server updates, placing all StatusChanges (including transfer StatusChanges) directly into `frameInput.statusChanges`. Injects matching pending full states via `ReconcileInjectPendingFullState()` into `currentFrames` at the matching frame to synchronize new cell data with the replay timeline. Gap detection iterates all coords to identify those that have progressed past their confirmed frame without server data for the current replay frame, tracking them in a `gapCoords` set — a coord is marked as having a gap when it is replayed past its confirmed frame but has no server data for that frame, meaning it ran with extrapolated inputs and CRC divergence is expected rather than a real desync. After each replayed frame, validates input CRCs per coord against server-reported values (logging input desyncs for diagnostics), then validates frame CRCs per coord against server-reported values, skipping coords in the gap set since their data divergence is expected; gap coords retain their old confirmed frame and will advance when the missing frames arrive via resends. On CRC mismatch, stores desync info (frame, coord, CRCs, deep-copied client Frame) into `ReconcileContext` for the main thread to handle. On CRC match, saves confirmed state for that coord inline at the CRC-validated frame (frame number and serialized frame stored into the `CoordReconcileWork`), so each coord's confirmed frame advances independently to its own last CRC-validated frame. Replay is capped at half the available consecutive frames per reconciliation tick. `ApplyReconcileResult()` detects desyncs, sends a desync report and debug frame request to the server, activates `SetDesyncDebugMode(true)` on the NetworkClient, and enters `DesyncDebugState`. While in desync debug state: `PollNetworkClient()` early-returns after checking for the debug frame response, and Main.cpp's main loop skips reconciliation, physics, and audio. When the debug frame arrives, `CompareWithServerFrame()` calls `ServerCompare()` for per-field comparison to pinpoint exact differing fields, then disconnects with a modal message. After replay, prunes non-active coords via `ReconcilePruneInactiveFrames()`, saves confirmed human state (Section 5: grid coord, player ID, armor, simulation time into `newConfirmedHumanState`), then performs predictive catch-up simulating with extrapolated inputs up to the main thread's current frame counter (`iTargetFrame`), storing `CoordExtrapolatedSnapshot` per coord per frame for CRC fast-path on subsequent ticks. `ApplyReconcileResult()` writes back per-coord results (new confirmed frame, serialized state, extrapolated snapshots) into `mCoordReconcileStates`, moves caught-up frames into `mCurrentFrames`, and updates the confirmed human state. The `CoordReconcileState` struct stores per-coord confirmed frame, serialized frame, server update buffer, extrapolated snapshots, an optional pending full state, and a `uiGeneration` counter that prevents stale reconcile results from writing back to a coord that was unsubscribed and resubscribed while the reconcile was in flight. Each `CoordReconcileWork` item carries the generation from the state at kick time; `ApplyReconcileResult()` skips write-back if the generation no longer matches (indicating the coord was recycled). The `ConfirmedHumanState` struct stores global human tracking state (grid coord, player ID, armor, simulation time).

**Soft Clock Correction** (`ComputeClockCorrectionNs()`): Called from Main.cpp after reconciliation to adjust the client's physics tick rate, keeping it slightly behind the server so server updates arrive before the client simulates those frames. Computes a target offset of `ceil(RTT/2 / frameTime) + 1` frames behind the server using `miLatestServerFrame` (tracked by `ApplyReceivedUpdates()`). The error (difference between current offset and target) drives a proportional correction clamped to +/-4 steps, each step being 1/64th of a frame's duration, applied to `mUpdateRemainderNs`. The clock error is also exposed so Main.cpp can reduce the frame deficit by the error before compensation, ensuring rollbacks help the correction converge rather than fighting it. This allows the CRC fast-path in `Reconcile()` to succeed routinely, eliminating constant rollback-and-replay. Returns 0ns if no server frames have been received yet. Feeds offset, target, and error values into `ProfileManagerBase::SetClockCorrection()` for smoothed display on the network profile screen.

`BuildFrameInputs` builds per-coordinate FrameInputs containing only status changes; player inputs are applied separately by the server and reconciliation systems.

**Server Networking Orchestration** (`GameServer.cpp`, `#ifdef BT_SERVER`): Ten server methods integrate with NetworkServer to manage multiplayer: `HandleDisconnectsServer()` drains pending disconnects from NetworkServer, converts them into `PendingPlayerDestroy` entries (capturing the player ID and grid coordinate), removes any matching clients from the spawn queue, and clears the client from `mDeadClientIds`; `HandleNewClientsServer()` queues unassigned clients for spawn (skipping clients in `mDeadClientIds` who haven't yet requested respawn); `ProcessSpawnRequestsServer()` converts network spawn/respawn requests (clearing the client from `mDeadClientIds` on spawn); `ComputeActiveSetServer()` unions all clients' subscribed coordinates (iterating each client's `coordSubscriptions` slots), and also ensures destroy coordinates are in the active set so the destroy StatusChange is processed and broadcast even if no other client is nearby; `BuildFrameInputsServer()` initializes per-coordinate FrameInputs for all active coordinates, injects spawn StatusChanges for clients waiting for initial spawn, injects `kDestroyPlayer` StatusChanges from `mPendingPlayerDestroys` into the appropriate coordinate's FrameInput (packing the player ID into the position vector), saves spawn StatusChanges into `mBroadcastSpawns` (transfers handled separately in `HarvestTransfersServer()`), takes a pre-spawn snapshot of player IDs for `FinalizeNewClientsServer()`, and clears `mBroadcastSpawns` at the start of each call to prevent stale data from prior physics frames; `HarvestTransfersServer()` tracks cross-cell entity transfers into `mBroadcastTransfers` and queues subscription updates with the transferred player's newly-spawned ID in the destination cell; `FinalizeNewClientsServer()` assigns spawned players to clients via `SendAssignPlayer()` and sends a kSpawned player state via `SendPlayerState()` (the client handles subscriptions, no full state sent here), diffs post-spawn player IDs against a pre-spawn snapshot, and calls `RefreshPreSpawnSnapshot()` to update the snapshot for subsequent physics frames in the same tick; `DetectPlayerDeathsServer()` iterates connected clients, checks if each client's human player still exists in their subscribed grid coordinate's frame, and when a player is missing (died), adds the client to `mDeadClientIds`, sends a `kServerPlayerState` packet with kDied via `SendPlayerState()`, and clears the client's `humanPlayerId` -- skips clients already in the dead set, clients waiting for spawn, clients mid-transfer (pending subscription update from `HarvestTransfersServer()`), or clients whose grid coordinate has no frame; `HandleSubscriptionUpdatesServer()` drains `PendingNewSubscription` entries from NetworkServer, validates each slot is still active and matches the expected coord on the client before sending full state via `SendCoordFullState()` (guarding against races where the client unsubscribes before the server processes the pending subscription), then sends player assignment (with the new player ID from the destination cell) via `SendAssignPlayer()` followed by a kChangedFrame player state via `SendPlayerState()` after grid transfers (the client handles subscription changes upon receiving the assignment); `BroadcastStatusChangesServer()` buffers unfiltered data (spawns, transfers, player inputs, and input CRC from `mFrameInputs`) to per-coord ring buffers via `BufferFrame()`, buffers full serialized frame snapshots via `BufferFullFrame()` for debug frame request responses, then calls `SendUpdate()` per client (which iterates each client's subscription slots internally) followed by `SendResends()` which sends separate unreliable packets per slot for any unacknowledged frames. The pre-physics methods (poll/disconnect/handle/spawn) are called from Main.cpp's server loop, while the post-physics methods (finalize/detect-deaths/subscribe/broadcast) are called per-physics-frame inside `UpdateFrames()` to ensure clients receive updates for every simulated frame.

**Human Player Tracking**: Identifies the human player by stable `player_t` ID rather than array index (indices shift due to swap-and-pop removal). Death detection is server-authoritative: the server detects when a player's ID disappears from the frame and sends a `kServerPlayerState` packet with kDied; the client processes these via `DrainReceivedPlayerStates()` to trigger the death screen. During replay playback, death is detected locally by checking the `idToIndexMap`. Monitors armor changes for camera shake. Tracks the human's grid coordinate across multi-frame transfers.

**Multi-Frame Grid Orchestration**: Manages the active set of grid coordinates and builds per-coordinate `FrameInput`. In client builds, the active set during gameplay is the human's cell plus neighbors (with origin always active); during the main menu, only the human's cell ({0,0}) is active (no neighbor frames are created). `BuildFrameInputs` applies server-confirmed inputs via extrapolation (see Client Networking above). In server builds, only human players exist -- `ComputeActiveSetServer()` computes the active set as the union of all connected clients' subscribed coordinates (iterating each client's slot-based `coordSubscriptions`), and `BuildFrameInputsServer()` builds per-coordinate FrameInputs with spawn and destroy StatusChanges for broadcasting. Creates frames at missing coordinates, ensures destination frames exist for buffer swaps, and garbage-collects frames outside the active set.

**Client-Driven Coord Subscriptions** (`UpdateSubscriptions()`/`TrySubscribeNext()`): The client manages which grid coordinates it subscribes to, replacing server-computed active sets. `UpdateSubscriptions()` computes desired coords based on player state: when alive (valid player ID), subscribes to the human's cell, all direct neighbors, and origin; when dead (invalid player ID but death screen active), subscribes to the death coord and origin for pre-emptive respawn readiness; when not yet assigned, subscribes to just origin. Desired coords are priority-ordered (human's cell first). Sends `SendUnsubscribe()` for slots whose coords are no longer desired, builds a subscription queue of desired coords not yet subscribed, and calls `TrySubscribeNext()` to begin subscribing. `TrySubscribeNext()` subscribes one coord at a time (sequential subscription): if any slot is in kSubscribing, kWaitingFullState, or kUnsubscribing state, it waits for that operation to complete before sending the next `SendSubscribe()`. Each full state reception in `ApplyReceivedFullStates()` calls `TrySubscribeNext()` to advance to the next coord in the queue. This sequential approach prevents overwhelming the server with simultaneous full state sends during grid transitions.

**Transfer Harvesting**: After carry-forward, reads transfer requests from active frames and spawns entities into destination cells via the `SpawnTransfer()` free function. In client builds, `HarvestTransfers()` spawns cross-cell transfers into destination NextFrames (matching server behavior) and tracks human player grid migration from local `transferRequests` (identifying the human's new player ID in the destination cell by taking the last player in the destination frame); during predictive catch-up, the client assumes no transfers occur and the CRC fast-path validates this assumption on the next server update. The single-player path in `HarvestTransfers()` preserves local transfer harvesting with entity spawning for non-networked play. In server builds, `HarvestTransfersServer()` collects all transfer requests from active frames, sorts them by type so spawn order matches network serialization's type-grouped order (ensuring client deserialization order equals server spawn order for deterministic replay), then spawns all transfers into destination cells. It also records transfers into `mBroadcastTransfers` and detects human player grid transfers across all connected clients, capturing the newly-spawned player ID from the destination cell and queuing `SubscriptionUpdate` entries for `HandleSubscriptionUpdatesServer()` to send player assignment (with the new ID) and full-state updates for newly-visible cells. During replay playback, skips human-cell transfers (handled by `ApplyTransferStatusChanges()` which processes transfer entries from the recorded stream and removes them before checksum validation).

**Spawn Orchestration**: Spawning and respawning are entirely server-driven. In server builds, `ProcessSpawnRequestsServer()` converts network spawn/respawn requests into `ClientSpawnInfo` entries (clearing the client from `mDeadClientIds` so it can be re-queued for spawn), `BuildFrameInputsServer()` injects spawn StatusChanges for waiting clients and calls `RefreshPreSpawnSnapshot()` to capture player IDs at the spawn coordinate, and `FinalizeNewClientsServer()` matches newly-spawned players to waiting clients by diffing post-spawn IDs against the snapshot, then sends player assignment via `SendAssignPlayer()` (the client handles subscriptions and full state requests), and calls `RefreshPreSpawnSnapshot()` again so subsequent physics frames in the same tick can correctly diff new spawns. `HandleNewClientsServer()` queues clients without assigned players for initial spawn (skipping dead clients). `Reset()` consolidates all human tracking state cleanup (player ID, armor, grid coordinate, pending changes).

**Persistence**: Quicksave via grid serialization (all frames plus human grid coordinate). Sound settings persisted separately. `ReplayMeta` struct captures human tracking state (grid coordinate, player ID, armor) and is persisted to a separate `.replay.meta` file for deterministic replay restore via `RestoreReplayMeta()`.

## Configuration Files

| File | Purpose |
|------|---------|
| `Pch.h` | Compile-time feature toggles: vcxproj defines either `BT_CLIENT` or `BT_SERVER` explicitly. `kbSingleInstance` is true for server builds. `kpcBuildConfigName` identifies the build configuration (Debug/Profile/Release) for client-server compatibility validation during the connection handshake. `kbEnableReconcileThread` controls whether reconciliation runs on a dedicated thread (currently enabled). `kbEnableFrameDispatch` controls whether Frame updates are dispatched in parallel via `Dispatch()` or run single-threaded (currently enabled; disable for debugging). `engine::NetworkSimulationLevel keNetworkSimulation` controls simulated packet loss and variable latency on network receive paths, supporting multiple region-based levels (`kDisabled`, `kEastCoast`, `kWestCoast`, `kEurope`, `kSouthAmerica`, `kChina`) with per-level latency and loss parameters (debug only; `kDisabled` in Profile and Release). `inline constexpr` toggles with `if constexpr` for zero-overhead conditional compilation.
