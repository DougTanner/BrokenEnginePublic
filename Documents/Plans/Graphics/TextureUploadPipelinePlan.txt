Texture Upload Pipeline Optimization Plan
==========================================

================================================================================
VALIDATION OF AUDIT FINDINGS
================================================================================

Finding 7.1 [Medium] -- Transfer queue fence wait blocks the upload thread per-frame
  Location: TextureUploadManager.cpp:188
  Status: PARTIALLY VALID

  The fence wait at line 188 does block the upload thread, but the actual impact
  is nuanced. The upload thread is gated by mFrameSignal (a binary semaphore
  released once per frame from Graphics.cpp:162), so it only runs once per frame
  anyway. The fence wait ensures the previous GPU transfer is complete before
  reusing the staging buffer. The real cost is:
    - CPU time spent in vkWaitForFences (potentially idle while GPU finishes)
    - The staging buffer cannot be filled while the GPU reads from it

  Double-buffering would allow the CPU to fill staging buffer B while the GPU
  reads from staging buffer A. However, this only helps when the GPU transfer
  takes longer than the CPU staging fill -- which is unlikely given the 4MB
  budget and PCIe bandwidth. The frame-gated signal means we submit at most
  once per frame regardless.

  Additionally, there is a second fence wait at line 388 (when a texture
  completes) that is truly blocking: it waits for the final submission before
  signaling completion. This is necessary for correctness because the LazyChunk
  state must not transition to kGpuUploadComplete until the GPU is done.

  RECOMMENDATION: Double-buffer the staging resources (buffer + command buffer +
  fence) to overlap CPU staging fill with GPU transfer. This is a modest win
  because the per-frame signal limits throughput to one submission per frame,
  but it eliminates the fence stall at line 188 in the common case where a
  multi-frame texture upload is in progress.

  SAFETY: Double-buffering is safe because:
    - The upload thread is the sole user of the staging buffer and transfer
      command buffer
    - No other thread touches these resources
    - The fence per slot ensures its staging buffer is not in-flight before reuse
    - The binary semaphore frame signal does not change

Finding 3.1 [Optimization Opportunity] -- Texture::Create allocates temporary staging buffers
  Location: Texture.cpp:207-257
  Status: VALID BUT LOW PRIORITY

  Each call to Texture::Create with a dataFunction allocates a staging buffer
  via Buffer::CreateBuffer, uses it, then destroys it. During init, this means
  many VMA alloc/free cycles. However:
    - This only happens at init time (not in the main loop)
    - VMA pools staging allocations efficiently
    - The allocations are different sizes per texture (mip chain total)
    - A shared staging buffer would need to be sized for the largest texture

  RECOMMENDATION: Create a shared init-time staging buffer in a new helper, or
  defer to the TextureUploadManager's existing staging buffer during init.
  However, this adds complexity for an init-only path. DEFER -- the current
  approach is correct and simple. If init time becomes a bottleneck, revisit.

  NOTE: Texture::Create and Texture::UpdateData also create OneShotCommandBuffers
  (which triggers Finding 4.1). Fixing 4.1 partially addresses this finding too.

Finding 4.1 [Optimization Opportunity] -- OneShotCommandBuffer creates/destroys VkCommandPool per use
  Location: OneShotCommandBuffer.cpp:6-54
  Status: VALID

  Every OneShotCommandBuffer construction creates a VkCommandPool, VkCommandBuffer,
  and VkFence. Destruction destroys all three. Usage sites:
    - Texture::Create (init-time, with dataFunction or layout transition)
    - Texture::UpdateData (runtime, rare)
    - Buffer::Create (init-time, for device-local buffers)
    - TextureCache (init-time, readback and BRDF LUT)
    - ProfileManagerBase (init-time, query pool reset)

  All uses are on the graphics queue from the main thread. A shared transient
  command pool with a cached fence would eliminate repeated pool create/destroy.

  RECOMMENDATION: Add a shared transient command pool + fence to DeviceManager
  (or a new lightweight holder). OneShotCommandBuffer allocates from the shared
  pool and resets the buffer on destruction, but does not destroy the pool/fence.

  SAFETY: All OneShotCommandBuffer uses are on the main thread targeting the
  graphics queue. No concurrent usage. A single shared pool is safe.

IMPLEMENTATION PLAN

PART 1: Double-buffer TextureUploadManager staging resources
------------------------------------------------------------
Moderate complexity, modest throughput improvement for multi-frame uploads.

Step 1.1: Add double-buffered resource arrays to TextureUploadManager.h

  File: Engine/Source/Graphics/Managers/TextureUploadManager.h

  Replace the single staging resource members (lines 39-45):
    VkCommandPool mTransferVkCommandPool
    VkCommandBuffer mTransferVkCommandBuffer
    VkFence mTransferVkFence
    VkBuffer mStagingVkBuffer
    VmaAllocation mStagingVmaAllocation
    VkDeviceSize mStagingSize
    void* mStagingMappedData

  With:
    static constexpr int kiStagingSlotCount = 2;

    VkCommandPool mTransferVkCommandPool = VK_NULL_HANDLE;

    struct StagingSlot
    {
        VkCommandBuffer vkCommandBuffer = VK_NULL_HANDLE;
        VkFence vkFence = VK_NULL_HANDLE;
        VkBuffer vkBuffer = VK_NULL_HANDLE;
        VmaAllocation vmaAllocation = VK_NULL_HANDLE;
        void* pMappedData = nullptr;
    };
    StagingSlot mStagingSlots[kiStagingSlotCount] {};
    int miCurrentSlot = 0;

  Rationale: One command pool is sufficient (command buffers are individually
  reset). Two slots allow ping-pong: fill slot B while slot A's fence is
  pending on GPU.

Step 1.2: Update InitTransferResources()

  File: Engine/Source/Graphics/Managers/TextureUploadManager.cpp
  Location: lines 18-56

  Keep the single VkCommandPool creation (line 29).
  Loop over kiStagingSlotCount to create per-slot:
    - VkCommandBuffer (allocate from the shared pool)
    - VkFence (created signaled)
    - VkBuffer staging buffer (4MB each, same CreateBuffer call)
    - Store pMappedData from VmaAllocationInfo

  Remove: mStagingSize member (it equals kiByteBudgetPerFrame always).

Step 1.3: Update DestroyTransferResources()

  File: Engine/Source/Graphics/Managers/TextureUploadManager.cpp
  Location: lines 58-118

  Replace the single fence wait (line 88) with a loop waiting on all slot fences.
  Replace the single staging buffer cleanup (lines 92-98) with a loop destroying
  all slot staging buffers, fences (do NOT destroy command buffers individually --
  they are freed when the pool is destroyed).
  Keep the command pool destruction at the end (line 116).

Step 1.4: Update UploadThread() to use double-buffered slots

  File: Engine/Source/Graphics/Managers/TextureUploadManager.cpp
  Location: lines 142-412

  At the top of each iteration (after mFrameSignal.acquire()):
    - Compute the current slot: StagingSlot& rSlot = mStagingSlots[miCurrentSlot];
    - Wait on rSlot.vkFence (this replaces the wait at line 188)
    - Use rSlot.vkCommandBuffer instead of mTransferVkCommandBuffer
    - Use rSlot.vkBuffer instead of mStagingVkBuffer
    - Use rSlot.pMappedData instead of mStagingMappedData
    - Use kiByteBudgetPerFrame instead of mStagingSize

  After vkQueueSubmit (line 383):
    - Advance: miCurrentSlot = (miCurrentSlot + 1) % kiStagingSlotCount;

  For the completion fence wait (line 388, inside `if (bDone)`):
    - Wait on the slot that was just submitted (the one BEFORE advancing):
      int iPrevSlot = (miCurrentSlot + kiStagingSlotCount - 1) % kiStagingSlotCount;
      Wait on mStagingSlots[iPrevSlot].vkFence

  The net effect: when processing texture T across frames N and N+1:
    - Frame N: wait on slot 0's fence (signaled from prior use), fill slot 0,
      submit, advance to slot 1
    - Frame N+1: wait on slot 1's fence (signaled from prior use), fill slot 1
      while slot 0's transfer may still be in flight, submit, advance to slot 0
    - The wait on slot 1 does NOT block on slot 0's transfer


PART 2: Shared transient command pool for OneShotCommandBuffer
--------------------------------------------------------------
Low complexity, eliminates per-use VkCommandPool create/destroy.

Step 2.1: Add shared command pool and fence to DeviceManager

  File: Engine/Source/Graphics/Managers/DeviceManager.h

  Add members:
    VkCommandPool mOneShotVkCommandPool = VK_NULL_HANDLE;
    VkFence mOneShotVkFence = VK_NULL_HANDLE;

Step 2.2: Create the shared pool in DeviceManager initialization

  File: Engine/Source/Graphics/Managers/DeviceManager.cpp

  After device creation, create:
    - VkCommandPool with VK_COMMAND_POOL_CREATE_TRANSIENT_BIT | VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT
      using miGraphicsQueueFamilyIndex
    - VkFence with VK_FENCE_CREATE_SIGNALED_BIT

  Destroy both in DeviceManager's DestroyResources (or destructor), BEFORE
  vkDestroyDevice.

    - Keep VkCommandBufferBeginInfo and vkBeginCommandBuffer as-is

  Destructor (lines 49-54):
    - Replace vkFreeCommandBuffers + vkDestroyFence + vkDestroyCommandPool with:
      vkFreeCommandBuffers(gpDeviceManager->mVkDevice,
          gpDeviceManager->mOneShotVkCommandPool, 1, &mVkCommandBuffer);

  Execute (lines 56-83):
    - Use gpDeviceManager->mOneShotVkFence instead of mVkFence

  File: Engine/Source/Graphics/OneShotCommandBuffer.h

  Remove members:

  These are now owned by DeviceManager.

Step 2.4: Update DeviceManager destroy order

  File: Engine/Source/Graphics/Managers/DeviceManager.cpp

  The shared command pool and fence must be destroyed AFTER all
  OneShotCommandBuffer users are done (which they are, since they're
  synchronous). Destroy them just before vkDestroyDevice in the
  DeviceManager's resource cleanup.
