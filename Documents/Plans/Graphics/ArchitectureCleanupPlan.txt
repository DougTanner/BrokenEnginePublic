Finding 7.2 -- Four near-identical terrain data pipeline creation blocks
  (PipelineManager.cpp:324-389)
  STATUS: VALID, WORTH FIXING
  The four blocks in CreateTerrainDataPipelines() share identical structure:
  same flags ({kRenderTarget, kPushConstants, kUpdateAfterBind}), same vertex
  shader, same vertex buffer, same descriptor layout (global UBO, islands
  storage buffer, combined samplers array). Only the pipeline enum, name,
  fragment shader, target texture, and source texture array differ. A
  data-driven loop eliminates ~50 lines of duplication.

Finding 7.3 -- Push constant setup duplicated across 5 Record* methods
  (Pipeline.cpp:175-281)
  STATUS: VALID, NOT WORTH FIXING
  RecordDraw, RecordDrawIndirect, RecordDrawIndirectSet2, RecordCompute, and
  RecordComputeIndirect each contain a 4-line push constant block. However,
  the stage flags differ between graphics (VERTEX|FRAGMENT) and compute
  (COMPUTE), RecordDrawIndirectSet2 has a distinct bind pattern, and the
  descriptor set binding logic differs across all five methods. Extracting
  a helper would save only the 4-line push constant block per method but
  would require passing the stage flags and pipeline bind point, adding
  complexity for minimal gain. The methods are each short (10-20 lines) and
  self-contained. Leave as-is per KISS.

Finding 7.4 -- Repetitive smoke/wind pipeline A/B pairs
  (PipelineManager.cpp:391-516)
  STATUS: VALID, NOT WORTH FIXING
  The smoke/wind pipelines use A/B ping-pong textures. While the clear
  pipelines (SmokeClearA/B, WindClearA/B) look similar, they target different
  textures. The spread pipelines (SmokeSpreadA/B, WindSpreadA/B) have
  meaningfully different shader references, descriptor layouts (SpreadA uses
  a storage buffer + different smoke texture + different swirl texture),
  and cross-reference each other's textures. Factoring these would require
  passing arrays of heterogeneous descriptor configs, producing a helper
  that's more complex than the original. The 8 pipelines are already grouped
  in a single well-named function. Leave as-is per KISS/YAGNI.

Finding 4.1 -- RecreateResources() four near-identical terrain texture
  recreation blocks (Graphics.cpp:452-493)
  STATUS: VALID, WORTH FIXING
  Four blocks follow the same pattern: check flag, get DetailTextureSize with
  a multiplier cvar, set extent width/height, call ReCreate(). Only the
  DestroyFlags enum, the cvar, and the target texture differ. A data-driven
  loop eliminates ~30 lines of duplication and makes adding new terrain
  channels trivial.

Finding 3.1 -- Refresh() is 170 lines of boilerplate (Graphics.cpp:235-403)
  STATUS: VALID, NOT WORTH FIXING
  Refresh() checks ~15 different cvars for changes and maps each to a
  DestroyType/DestroyFlags combination. While repetitive, each block has
  unique logic: some set multiple destroy flags, some have conditional guards
  (gpInstanceManager != nullptr, gpTextureManager != nullptr), some log
  different messages, and some combine multiple cvar checks into one block.
  A table-driven approach would need to encode the conditional guards,
  multi-flag sets, and combined cvar checks, producing a more complex
  abstraction than the current linear code. The function is read-rarely
  settings-change code. Leave as-is per KISS.

Finding 1.1 -- Pipeline::Create hardcodes model descriptor injections
  (Pipeline.cpp:38-71)
  STATUS: VALID, NOT WORTH FIXING
  Pipeline::Create auto-injects 5 descriptors (lighting, shadow, smoke, mesh
  data, joint matrices) after any kModel descriptor. This is intentional
  coupling: model pipelines always need these descriptors, and centralizing
  the injection here prevents every model pipeline creation site from
  repeating the same 5 descriptors. The magic number 5 is documented with
  a comment. Moving this elsewhere would just move the coupling, not
  eliminate it. Leave as-is.

Finding 1.2 -- MRT lighting pass bypasses Texture::RecordBeginRenderPass
  (CommandBufferManager.cpp:228-256)
  STATUS: VALID, WORTH FIXING
  The MRT lighting pass at line 228-255 manually constructs a
  VkRenderPassBeginInfo and calls vkCmdBeginRenderPass directly, while every
  other render pass in the file uses Texture::RecordBeginRenderPass (either
  instance or static). The MRT pass needs to use a shared render pass and
  framebuffer (mLightingVkRenderPass, mLightingVkFramebuffer) that writes to
  3 color attachments simultaneously, which the instance method doesn't
  support (it uses a single texture's own render pass/framebuffer). However,
  the static Texture::RecordBeginRenderPass already exists and accepts
  arbitrary render pass/framebuffer/extent parameters. The manual code should
  use this static method for consistency, reducing the 12-line manual block
  to a single call.

Finding 5.1 -- Non-contiguous binding numbers in Global Set 0
  (TextureDescriptors.cpp:23-29)
  STATUS: VALID, NOT WORTH FIXING
  Bindings are 0, 1, 3, 4, 12 with gaps at 2 and 5-11. This is intentional:
  bindings 0 and 1 (uniform buffers) are shared with per-pipeline Set 1
  layouts, and binding 3/4/12 are assigned to match shader expectations
  (samplerRepeat at 3, textures at 4, samplerClamp at 12). Renumbering
  would require updating all GLSL shaders that reference these bindings and
  would break the deliberate alignment with per-pipeline set layouts. Vulkan
  explicitly supports non-contiguous bindings. Leave as-is.

2a. Replace the four near-identical if-blocks (kTerrainElevation through
    kTerrainAO) with a data-driven loop:

    struct TerrainTextureRecreateDesc
    {
        DestroyFlags eFlag;
        Cvar& rMultiplierCvar;
        Texture& rTexture;
    };

    TerrainTextureRecreateDesc pTerrainDescs[]
    {
        {DestroyFlags::kTerrainElevation, gTerrainElevationTextureMultiplier, gpTextureManager->mRenderTargetTextures.mTerrainElevationTexture},
        {DestroyFlags::kTerrainColor, gTerrainColorTextureMultiplier, gpTextureManager->mRenderTargetTextures.mTerrainColorTexture},
        {DestroyFlags::kTerrainNormal, gTerrainNormalTextureMultiplier, gpTextureManager->mRenderTargetTextures.mTerrainNormalTexture},
        {DestroyFlags::kTerrainAO, gTerrainAmbientOcclusionTextureMultiplier, gpTextureManager->mRenderTargetTextures.mTerrainAmbientOcclusionTexture},
    };

    for (const auto& rDesc : pTerrainDescs)
    {
        if (mDestroyFlags & rDesc.eFlag)
        {
            if (gpTextureManager != nullptr)
            {
                auto [iX, iY] = gpTextureManager->DetailTextureSize(rDesc.rMultiplierCvar.Get());
                rDesc.rTexture.mInfo.extent.width = static_cast<uint32_t>(iX);
                rDesc.rTexture.mInfo.extent.height = static_cast<uint32_t>(iY);
                rDesc.rTexture.ReCreate();
            }
        }
    }

    Note: The Cvar type used for rMultiplierCvar must match the actual cvar
    type. Check declaration of gTerrainElevationTextureMultiplier etc. to
    confirm the type name.
