Draw Call Batching Plan
=======================

VALIDATION
----------

Finding 5.1 [Medium] -- Per-material pipeline binds in model rendering
  Location: ModelPipeline.h:23, ModelPipeline.cpp:82-117
  Status: PARTIALLY VALID -- the observation is accurate but the severity is overstated.

  Each ModelPipeline creates N Pipeline objects (one per material) with separate
  VkPipeline handles. In RecordDrawIndirect, the multi-set (kMultiSet) path already
  optimizes by binding Set 0 + Set 1 once before the material loop (line 88-93).
  Inside the loop, RecordDrawIndirectSet2 still calls per-material:
    - vkCmdPushConstants (material index)
    - vkCmdBindPipeline
    - vkCmdBindDescriptorSets (Set 2 only)
    - vkCmdBindVertexBuffer (redundant -- same buffer every iteration)
    - vkCmdDrawIndexedIndirect (drawCount=1)

  HOWEVER, the per-material VkPipeline objects are genuinely different Vulkan
  pipelines in cases where alpha blending state differs. ModelPipeline::Create
  (line 44-59) sets kAlphaBlend on transparent materials, which changes the
  VkPipelineColorBlendAttachmentState baked into the VkPipeline at creation time.
  Opaque and transparent materials CANNOT share a VkPipeline.

  For materials that share the same pipeline state (all-opaque or all-transparent
  within a group), the pipeline bind is redundant -- Vulkan drivers optimize
  redundant vkCmdBindPipeline calls, but it still adds command buffer overhead.

  The real waste is:
  1. Redundant vkCmdBindVertexBuffer calls (same buffer every material)
  2. Separate indirect buffers per material (prevents multi-draw)
  3. Separate VkPipeline objects for opaque materials that have identical state


Finding 5.2 [Medium] -- Single-draw indirect calls (count = 1)
  Location: Pipeline.cpp:229, Pipeline.cpp:250
  Status: VALID but structurally constrained.

  Every vkCmdDrawIndexedIndirect call uses drawCount=1. The indirect buffer layout
  stores one VkDrawIndexedIndirectCommand per command buffer index (per-framebuffer),
  not per material. Each Pipeline owns its own indirect buffer.

  Multi-draw-indirect (drawCount > 1) requires all draws to share the same
  VkPipeline, descriptor sets, and vertex buffer binding -- which is already the
  case for opaque materials within a ModelPipeline that share identical blend state.

  A contiguous array of VkDrawIndexedIndirectCommands for all same-state materials
  could be drawn with a single vkCmdDrawIndexedIndirect(drawCount=N).


FEASIBILITY ANALYSIS
--------------------

What CAN be batched:
  - Opaque materials within the same ModelPipeline share the same shaders, vertex
    buffer, Set 0, Set 1, and pipeline state (depth test, cull, sample shading).
    They differ ONLY in Set 2 (per-material textures) and push constants (material
    index). Since the shader already indexes into a materials storage buffer via
    push constant, and textures use bindless indexing via Set 0, the per-material
    Set 2 differences are the main obstacle.

  - The kMultiSet architecture already puts shared bindings (uniform buffers, storage
    buffers, lighting, shadow, smoke, mesh data, joint matrices) in Set 1, and
    per-material bindings (model-specific PBR textures) in Set 2.

  - Looking at PipelineDescriptorWriter.cpp:161-189, the model material storage
    buffer (containing all PBR material data for all materials) is already uploaded
    once per ModelPipeline and shared across materials. The shader uses the push
    constant material index to index into this buffer.

  - Textures use bindless indexing: CrcToIndex maps texture CRCs to indices in the
    global texture array (Set 0). Material texture indices are stored in the
    PbrMaterialLayout storage buffer. The per-material Set 2 bindings are for the
    irradiance, prefiltered, LUT BRDF, and material storage buffer -- but these are
    IDENTICAL across all materials in the same ModelPipeline.

What CANNOT be batched:
  - Opaque vs transparent materials (different VkPipeline blend state).
  - Different ModelPipelines (different vertex buffers, different scene data).
  - The draw pass filtering (kOpaque vs kTransparent) already handles separation.

KEY INSIGHT: Since the kMultiSet path already shares Set 0 and Set 1, and Set 2
contains only data that is identical across materials (irradiance, prefiltered,
LUT BRDF, and the shared materials storage buffer), the per-material Set 2 bind
in RecordDrawIndirectSet2 is actually REDUNDANT for materials with the same
pipeline state. The only per-material differences are:
  1. Push constants (material index in f4PushConstants.w)
  2. The VkPipeline handle (which is identical for same-blend-state materials)
  3. The indirect buffer (which is per-Pipeline, preventing multi-draw)

IMPLEMENTATION PLAN
-------------------

Phase 1: Remove redundant vertex buffer binds in multi-set path
  Impact: Minor CPU overhead reduction
  Risk: Very low

  Step 1.1: Move vertex buffer bind out of per-material loop
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp
    Line: 87-116

    In RecordDrawIndirect, after the bMultiSet check (line 88), bind the vertex
    buffer once before the material loop:

      if (bMultiSet)
      {
          VkDescriptorSet sets[2] = {...};
          vkCmdBindDescriptorSets(...);
          mpPipelines[0].mInfo.pVertexBuffer->RecordBindVertexBuffer(vkCommandBuffer);
      }

    Then modify RecordDrawIndirectSet2 to skip the vertex buffer bind.

  Step 1.2: Add a new RecordDrawIndirectSet2NoVB method (or add a bool parameter)
    File: Engine/Source/Graphics/Objects/Pipeline.h
    Line: 104

    File: Engine/Source/Graphics/Objects/Pipeline.cpp
    Line: 232-251

    Option A (simpler): Remove the RecordBindVertexBuffer call from
    RecordDrawIndirectSet2, since ModelPipeline always binds it before the loop.
    This is safe because RecordDrawIndirectSet2 is ONLY called from
    ModelPipeline::RecordDrawIndirect.

    Option B: Add a parameter to skip the bind. Option A is preferred (KISS).


Phase 2: Share VkPipeline objects for same-state opaque materials
  Impact: Reduces vkCmdBindPipeline calls for opaque materials to 1 per model
  Risk: Low

  Step 2.1: Create one opaque VkPipeline and one transparent VkPipeline per model
    File: Engine/Source/Graphics/Objects/ModelPipeline.h
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp

    Currently, ModelPipeline::Create creates N Pipeline objects (one per material).
    Each opaque material gets an identical VkPipeline. Instead:

    - Create at most 2 VkPipeline objects: one opaque, one transparent (if needed)
    - Store which pipeline each material uses (index 0 or 1)
    - All materials still need their own indirect buffer and Set 2 descriptor sets

    However, this requires refactoring how Pipeline objects are structured. Each
    Pipeline currently owns its own VkPipeline + indirect buffer + descriptor sets.
    Splitting these apart is a significant refactor.

    RECOMMENDATION: Skip this phase. The Vulkan driver already detects redundant
    pipeline binds and short-circuits them. The cost is a few CPU cycles per
    redundant call, not a GPU state change. This optimization would add complexity
    for minimal real-world benefit, violating KISS/YAGNI.


Phase 3: Multi-draw-indirect for same-pipeline materials
  Impact: Reduces draw calls from N to 1 per pipeline state group
  Risk: Medium -- requires restructuring indirect buffer layout

  Step 3.1: Consolidate indirect buffers into ModelPipeline
    File: Engine/Source/Graphics/Objects/ModelPipeline.h
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp

    Instead of each Pipeline owning a separate indirect buffer, ModelPipeline
    allocates a single contiguous buffer with N VkDrawIndexedIndirectCommands per
    command buffer index (where N = miMaterialCount).

    Layout: [cb0_mat0, cb0_mat1, ..., cb0_matN, cb1_mat0, cb1_mat1, ...]

    New member in ModelPipeline:
      VkBuffer mIndirectVkBuffer = VK_NULL_HANDLE;
      VkDeviceMemory mIndirectVkDeviceMemory = VK_NULL_HANDLE;
      VmaAllocation mIndirectVmaAllocation = VK_NULL_HANDLE;
      VkDrawIndexedIndirectCommand* mpIndirectMappedMemory = nullptr;

  Step 3.2: Update WriteIndirectBuffer to write into consolidated buffer
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp
    Line: 119-133

    Change WriteIndirectBuffer to write all material commands into the shared buffer
    at the correct offsets. For command buffer index i and material index j:
      offset = (i * miMaterialCount + j) * sizeof(VkDrawIndexedIndirectCommand)

  Step 3.3: Update RecordDrawIndirect to use multi-draw for same-state groups
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp
    Line: 82-117

    For the multi-set path, group consecutive opaque materials and draw them with
    a single vkCmdDrawIndexedIndirect(drawCount=N, stride=sizeof(VkDrawIndexedIndirectCommand)).

    PROBLEM: The push constant material index (f4PushConstants.w) changes per
    material. With multi-draw-indirect, there is no way to change push constants
    between draws. The shader uses this index to look up material data from the
    storage buffer.

    SOLUTION: Use gl_DrawID (VK_KHR_shader_draw_parameters, core in Vulkan 1.1)
    as the material index instead of the push constant. gl_DrawID increments per
    draw within a multi-draw call, starting from 0.

    However, gl_DrawID starts from 0 for each vkCmdDrawIndexedIndirect call, so
    we need to either:
    a) Ensure the indirect buffer ordering matches material indices exactly
    b) Add a base material index push constant per batch

    Since we control the indirect buffer layout and materials are sequential,
    option (a) works if we draw all opaque materials as one batch (skipping
    transparent ones by setting instanceCount=0 in the indirect command).

  Step 3.4: Modify the vertex/fragment shaders to use gl_DrawID
    File: (shader source files -- model vertex/fragment shaders)

    Replace push constant material index usage with gl_DrawID. The material index
    pushed in f4PushConstants.w would become the base index, and gl_DrawID provides
    the offset.

    Actually, since the indirect buffer already has the correct firstIndex and
    indexCount per material, and the material storage buffer is indexed by material
    index, gl_DrawID can directly replace the push constant material index IF:
    - All materials are included in the multi-draw (transparent ones with
      instanceCount=0 to skip them)
    - The draw order matches the material array order

  Step 3.5: Set instanceCount=0 for skipped materials
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp

    In WriteIndirectBuffer, when a material should be skipped for a given pass
    (e.g., transparent material in opaque pass), set instanceCount=0. This lets
    the GPU skip the draw without CPU-side filtering.

    In RecordDrawIndirect, instead of the per-material loop with pass filtering,
    issue a single vkCmdDrawIndexedIndirect with drawCount=miMaterialCount.

    For kOpaque pass: WriteIndirectBuffer sets instanceCount=0 for transparent materials
    For kTransparent pass: WriteIndirectBuffer sets instanceCount=0 for opaque materials
    For kAll pass: All materials get their instance count

    PROBLEM: WriteIndirectBuffer is called once per frame, not once per pass. The
    opaque and transparent passes within the same frame need different instance counts
    for the same materials. This means we need either:
    a) Separate indirect buffers for opaque and transparent passes
    b) Two regions in the same buffer
    c) GPU compute to set up indirect commands per pass

    Option (a) doubles memory but is simplest. Option (b) is the same thing.
    Option (c) is overengineered.

    REVISED APPROACH: Keep the per-material indirect buffers as-is (one per Pipeline
    in the mpPipelines array). For multi-draw, copy the relevant commands into a
    contiguous staging region before recording. But this requires main-loop memory
    allocation or a pre-allocated scratch buffer.

    ALTERNATIVELY: Since the existing per-material indirect buffers are already
    host-visible and mapped, we can pass the first material's buffer offset and
    stride to vkCmdDrawIndexedIndirect -- BUT indirect commands for different
    materials are in DIFFERENT VkBuffers, so they cannot be multi-drawn.

    This confirms that Phase 3 requires consolidating indirect buffers (Step 3.1)
    AND solving the dual-pass problem. The cleanest approach:

    - ModelPipeline owns TWO consolidated indirect buffers:
      1. mOpaqueIndirectBuffer (commands for opaque materials only, packed contiguously)
      2. mTransparentIndirectBuffer (commands for transparent materials only, packed)
    - WriteIndirectBuffer fills both, using separate counts:
      miOpaqueDrawCount and miTransparentDrawCount
    - RecordDrawIndirect issues one multi-draw per pass

  Step 3.6: Update Pipeline to not create indirect buffers for multi-set materials
    File: Engine/Source/Graphics/Objects/Pipeline.cpp
    File: Engine/Source/Graphics/Objects/PipelineCreator.cpp
    Line: 234-261

    When bFromMultimaterial is true, skip indirect buffer creation in
    PipelineCreator::CreateGraphicsPipeline. The ModelPipeline will own the
    consolidated buffers instead.

    Add a new flag or parameter to Pipeline::Create to signal this.

  Step 3.7: Bind Set 2 once (it is shared across materials in kMultiSet)
    File: Engine/Source/Graphics/Objects/ModelPipeline.cpp

    Since all materials in a kMultiSet ModelPipeline share the same Set 2 content
    (irradiance, prefiltered, LUT BRDF, materials storage buffer), bind Set 2
    once alongside Set 0 and Set 1, before the multi-draw call.

    This eliminates per-material descriptor set binds entirely.


RECOMMENDED IMPLEMENTATION ORDER
---------------------------------

Phase 1 only.

Phase 1 is a clean, low-risk optimization that removes genuinely redundant work
(N-1 redundant vkCmdBindVertexBuffer calls per model per frame). It follows KISS
and can be done in a single small change.

Phase 2 should be skipped (YAGNI -- driver handles redundant pipeline binds).

Phase 3 is architecturally sound but involves significant refactoring:
  - Restructuring indirect buffer ownership
  - Shader changes (gl_DrawID)
  - Dual-buffer scheme for opaque/transparent passes
  - Changes to Pipeline creation flow

The real-world draw call count for models is bounded by the number of unique model
types times their material counts. With typical game scenes (tens of model types,
1-8 materials each), we are talking about tens to low hundreds of draw calls total
for models. This is well within comfortable CPU/GPU overhead for modern hardware.

Phase 3 should be deferred until profiling shows model draw calls are a bottleneck
(e.g., hundreds of unique model types on screen simultaneously).
