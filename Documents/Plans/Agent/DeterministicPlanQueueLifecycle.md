# Move deterministic plan-queue lifecycle into AgentCli

## Context

The current planning workflow makes agents parse and mutate `Documents/Plans/Order.md` themselves. `/create-follow-up-plans` writes rows and prose metadata under a queue lock, while `/next-plan` separately enumerates orphans, parses free-form dependency language, selects a row, claims it through a sidecar, and later performs row/file/reference cleanup. Small queue-only edits therefore trigger repeated reviewer passes and duplicate mechanical logic across skills.

AgentCli already owns the correct cross-worktree coordination primitives. Queue locks and row claims live beneath the PC-global `BrokenEngineLocks` store and are keyed by canonical Git common directory plus normalized `Order.md`/plan identity, so every worktree sees the same ownership state. `Order.md` itself is ordinary Git content and is not shared between worktrees: the clean primary/root checkout is the live queue used for selection, while a session worktree contains proposed add/update/complete changes that become live only after verified landing advances the primary branch.

AgentCli should own the mechanical `Order.md` format and lifecycle. Plan-producing agents decide content, scoring, grouping, and semantic constraints, write or stage the plan files, then give AgentCli a structured request. Plan-consuming agents ask AgentCli to validate the current primary queue and atomically claim one eligible plan path. Row order alone cannot encode prerequisites while preserving concurrent plan sessions, so add one structured dependency column and retain selected rows until terminal completion.

## Design

1. Extend AgentCli with a `plan order` target whose `validate`, `add`, `update`, `claim-next`, and `complete` verbs operate on the repository queue files and the existing plan queue/row coordination domain. Do not add a PowerShell parser, another lock domain, or repository claim metadata.
2. Bind every repository-file operation explicitly:
    - `--repo` remains the canonical Git common directory used for global coordination identity.
    - `--primary-worktree` is the wrapper-provided `BROKEN_ENGINE_PRIMARY_CHECKOUT`; AgentCli proves it is the registered primary checkout for `--repo`, is attached to the supplied target branch, and resolves the live queue paths beneath it.
    - `--worktree` is the wrapper-provided session checkout; AgentCli proves it is a registered worktree for the same common directory and resolves every queue, plan, staged-content, and request path beneath it without reparse traversal.
    - `validate` names the exact worktree tree to inspect. `claim-next` reads primary but also validates the session. `add`, `update`, and `complete` mutate only the session worktree, except when the explicitly authorized checkout is itself the primary/root checkout.
3. Make the executable table mechanically owned with columns `Plan | Tier | Effort | Impact | Risks | Score | Depends On | Notes`. `Depends On` is `-` or a semicolon-separated list of normalized repository-relative `Documents/Plans/<area>/<file>.md|.txt` and `Documents/Features/<area>/<file>.md|.txt` identities. AgentCli rejects rooted paths, raw `..`, case/slash aliases, duplicates, self-dependencies, missing dependency rows, and cycles. Notes may contain ordinary prose; the parser uses the fixed leading columns and final row delimiter rather than naïvely splitting embedded `|` characters in Notes.
4. `plan order validate` reads both Plans and Features queues from the named worktree and emits deterministic JSON plus stable path/line/code diagnostics for malformed rows, wrong `Effort - Impact + Risks`, duplicate identities, missing plan files, unindexed executable `.md`/`.txt` files, executable/reference-document overlap, invalid dependencies, and cycles. Reference/index tables remain non-executable and must resolve. Score order remains approximate and produces no diagnostic. Strict UTF-8 decoding, bounded input sizes, and byte-preserving writes protect the file/request trust boundaries.
5. `plan order add --request <json>` accepts a schema-versioned request canonically contained beneath the session worktree's `Temp/`. Each entry supplies the destination queue, plan path, Tier/Effort/Impact/Risks/Notes fields, and optional dependencies on already-live plans. The request groups new entries into prerequisite-first sequences; AgentCli adds an immediate-predecessor edge within each sequence, so `[A, B, C]` becomes `B depends on A` and `C depends on B`. Independent plans use separate sequences. AgentCli computes Score, treats the pre-existing new plan files as prospective non-orphans, validates the complete two-queue graph, locks both existing queue identities in canonical path order, re-reads/revalidates, adds all rows or none, and releases in reverse order.
6. New plan files intentionally exist before `add`: `/save-plan` and `/create-follow-up-plans` finish semantic validation and write them in their session, then call AgentCli. A failed add leaves retryable orphan input files and no new rows. Those plans are not live to other sessions until the session lands into primary; primary `validate`/`claim-next` never sees unlanded additions.
7. `plan order update --request <json>` preserves `/create-follow-up-plans`' existing-plan extension path. The skill writes proposed plan bytes beneath session `Temp/` and supplies the target identity, expected original file/row hashes, replacement row fields/dependencies, and staged-content path. Under both queue locks, AgentCli requires the target row to be unclaimed, rechecks the hashes, treats staged plan bytes as opaque content, atomically publishes the plan-file/row/graph update, and validates both queues. A claim/hash conflict produces zero repository mutation; AgentCli never authors or semantically rewrites plan prose.
8. `plan order claim-next` accepts the global owner/session identity, optional explicit plan, both order paths, authoritative primary checkout/target branch, and clean session worktree. It acquires both existing queue locks in canonical order and reads the current clean primary/root queue. Before claiming, it requires the session `HEAD` to equal the primary target-branch `HEAD` and the session's selected plan bytes to match the primary plan bytes; otherwise it returns a stale-session result without a claim. It validates the primary graph, reads global row claims, and selects the first row in the requested queue that is unclaimed and whose dependency rows are absent.
9. A dependency row remains blocking while it exists, including while claimed by another session. Automatic selection may continue to an unrelated eligible row; explicit selection returns exact dependency/claim blockers. `claim-next` creates the existing global row claim and returns JSON containing normalized plan path, row fields, dependency disposition, primary commit, Order/plan hashes, claim metadata, and lock/unlock results. Persist those primary identities in the row-claim metadata so later status/finalization can prove what was selected.
10. `claim-next` does not edit `Order.md` or delete the plan file. Keeping the row until completion preserves durable queue/dependency state across implementation, rejection, deferral, crashes, and concurrent sessions. A stale registered worktree can never resurrect a completed plan after its claim is released because all future selection reads the current primary queue and requires an exact primary/session baseline match.
11. `plan order complete --plan <path> --owner <token>` requires the matching owned row claim and terminal cleanup authorization. In the session worktree it locks both queues, validates, removes the executable row and plan file, removes that identity from structured `Depends On` cells, validates the prospective graph, and publishes the handled transaction. The global row claim remains until `/finalize-changes` verifies that the cleanup landed and performs the existing owner-only `plan row unclaim`.
12. Complete is idempotent for reconciliation. If finalization rebases the session over a newer primary queue, it invokes `complete --reapply` after semantic conflict resolution and before regenerating final-tree verification. Reapply requires the same owned claim, accepts an already-absent target row/file, removes any newly introduced dependency edges, and emits a new receipt bound to the exact reconciled bytes. The final ledger must contain that receipt and a fresh `validate` PASS. Finalization performs no ad-hoc Markdown lifecycle edits, but it may invoke this AgentCli reapplication inside its existing reconcile/reverify loop.
13. Queue-changing primary advancement participates in the same coordination. `/finalize-changes` acquires the landing lock first, then the Plans/Features queue locks in canonical order immediately around the final clean-primary identity check and primary ref advance, and releases queue locks before the landing lock. This prevents `claim-next` from reading a mixed primary queue while a queue-changing landing advances the target branch. Non-queue landings do not acquire plan queue locks.
14. Add/update/complete use prospective bytes and retain exact originals through the commit point. Handled parse, validation, or write failures before commit restore the original state. After a complete validated state commits, an unlock failure retains the full post-state and reports the exact unreleased lock without unsafe rollback. Abrupt process termination, machine failure, and power loss remain out of scope.
15. Replace prose prerequisite interpretation with structured dependencies. Migrate every live directional prerequisite into `Depends On`. Mandatory nondirectional constraints (`never interleave`, joint resolution, alone execution, protocol/version/CRC/replay/`.pack`/`kiVersion` batches) move into reciprocal standard `## Coordination` sections in every affected live plan. Creating or changing such a constraint requires an atomic `update` request for every existing counterpart; if any counterpart is claimed or changed, the whole add/update fails with exact claim/hash evidence for manager coordination. Ordinary warning-only overlap may remain one-sided in the new/updated plan and does not block queue mutation. After migration, delete `## Dependencies` and `## File Groups` from both Order files.
16. Simplify the skill boundaries:
    - `/create-follow-up-plans` retains evidence adjudication, semantic duplicate detection, grouping, plan prose, scoring, and coordination decisions. It writes new files, stages existing-plan/reciprocal Coordination updates, builds one add/update request with independent sequences and explicit dependencies, invokes AgentCli, and never edits/parses Order directly.
    - `/save-plan` writes the destination plan, creates a single-entry add request, and delegates row insertion/validation to AgentCli.
    - `/next-plan` calls primary `validate` and then `claim-next`, replacing its Markdown dependency parser, manual queue-lock choreography, and `Invoke-PlanRowClaim.ps1` sidecar. A legacy primary orphan blocks selection; the existing research/scoring path adopts it through `add`, lands that queue-only repair, and restarts from a fresh session before selection. Relevance checking, current-code research, source capture, synthesis, audit, grill, approval, and implementation authority remain agent-owned.
    - `/next-plan` synthesis preserves the source plan's `## Coordination` verbatim except for approved current path/symbol refreshes. It uses `complete` only on successful execution or explicitly approved obsolete/abandoned cleanup. Rejection and deferral retain row/file state and use the existing owner-only row-unclaim route after the appropriate landing/safe-stop contract.
    - `/verify-changes` runs session `validate` after the final mutation and records its PASS plus the relevant add/update/complete receipt.
    - `/finalize-changes` owns reconciliation-time `complete --reapply`, regenerated verification when needed, coordinated queue-changing primary advancement, and post-landing row unclaim.
17. Keep semantic overlap/deduplication, scoring, plan prose, and user decisions in the manager/skills. AgentCli owns normalized identities, table/graph validity, primary-vs-session freshness, deterministic selection, global ownership, and mechanical mutation only.
18. Preserve and reconcile the concurrent `Agent/BoundAgentContextAndCapabilityReporting.md` changes in `.agents/skills/next-plan/SKILL.md` and `.agents/skills/finalize-changes/SKILL.md`. Refresh integration anchors from the settled tree and do not overwrite its bounded-report/context-lifecycle work.

## Out of scope

- LLM judgment inside AgentCli: semantic duplication, score selection, plan quality, overlap importance, or prose rewriting.
- Removing global row claims, queue locks, wrapper session claims, or landing locks.
- Removing a selected row at claim time or persisting active owner/session metadata in repository files.
- Strict score sorting, automatic re-scoring, or using row position as a substitute for dependencies.
- Allowing selection from a stale session snapshot or treating unlanded session queue edits as live primary state.
- Persistent journaling or recovery from abrupt process termination, machine failure, or power loss.
- Reopening `Engine/ReleaseStaticAnalysisGateEnforcement.md`, engine/runtime behavior, unit tests, or a general Markdown library.

## Acceptance criteria

- AgentCli is the only component that parses or mutates executable Order rows and the only component that selects/claims the next plan; updated skills contain no Markdown row/dependency parser or direct Order edit instructions.
- Global queue locks/row claims remain keyed by Git common directory, while file operations prove the authoritative primary and registered session worktrees, enforce containment, and distinguish live primary state from proposed session changes.
- `validate` deterministically diagnoses malformed rows, arithmetic errors, duplicates, missing files, orphans, reference overlap, missing/self/cyclic dependencies, unsafe paths, and dirty/unverifiable primary authority; approximate score order passes silently.
- Add accepts prewritten plan files plus structured row data, preserves independent prerequisite-first sequences, computes Score, and adds all rows or none. Failure leaves explicit retryable session orphans that are not visible in primary until landed.
- Update publishes staged opaque plan bytes plus row/dependency changes only when original hashes still match and every affected existing row is unclaimed; claimed reciprocal Coordination updates fail atomically.
- Claim-next reads the current clean primary queue under global locks, requires an exact primary/session commit and plan-byte match, returns and globally claims the first eligible path, and makes no repository edit. Claimed prerequisites block dependents while unrelated plans remain concurrently selectable.
- A stale worktree cannot reclaim a plan after another session lands completion and unclaims it. Fixtures cover a pre-landing stale worktree, current-primary selection, post-landing unclaim, and rejected stale reclaim.
- Complete requires the row owner, removes session row/file/dependency edges transactionally, survives finalization reconciliation through idempotent reapply, and leaves the claim until the exact cleanup lands. The final verification receipt binds the reconciled bytes.
- Queue-changing primary landing holds landing then queue locks during the final ref advance; claim-next cannot observe a mixed root queue. Lock acquisition/release ordering has contention and failure fixtures.
- Every current directional dependency is structured; every still-relevant mandatory nondirectional constraint is reciprocal in plan-body Coordination before old Dependencies/File Groups sections are removed. Ordinary overlap remains nonblocking.
- Handled pre-commit failures restore exact bytes; post-commit unlock failures retain a complete validated state and report the unreleased lock. No power-loss guarantee is claimed.
- `/create-follow-up-plans`, `/save-plan`, and `/next-plan` exercise add/update, orphan repair-and-land, automatic/explicit claim-next, dependency blocking, rejection/deferral retention, obsolete cleanup, successful completion, and reconciliation reapply only through AgentCli.
- AgentCli fixtures cover both queues/reference documents, independent sequences, prerequisite chains, existing/cross-queue dependencies, cycles, claimed-prerequisite concurrency, duplicate/orphan/missing paths, existing-plan update, reciprocal claimed counterpart, primary/session mismatch, owner mismatch, Complete reapply, edge pruning, rollback, Unicode/newlines, malformed requests/files, and queue-changing landing contention.
- AgentCli Release/x64 rebuild and command smoke tests pass through `/compile`; `--help` and `Test-AgentCliCapabilities.ps1` attest `plan order`; changed skills pass `/validate-skill`; `/update-vcxproj`, `git diff --check`, and final-tree `plan order validate` pass.

- Score: Effort 5, Impact 4, Risks 3, total 4; Tier Architectural. The scope includes an AgentCli C++ command surface, global/root/session coordination, finalization integration, and one-time migration across the live plan corpus.
- Historical duplicate disposition: `PlanQueueScoreOrderValidation.md` is not revived; strict score-order enforcement remains rejected.
