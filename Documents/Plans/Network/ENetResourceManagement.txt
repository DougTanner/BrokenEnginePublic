ENet Resource Management: Null Checks and Workbuffer RAII Guards
================================================================

Three small fixes for ENet resource handling in the network layer.

=== Part A: Missing enet_host_create() Null Checks ===

Problem: enet_host_create() can return nullptr (e.g., socket bind failure).
Both Client and Server immediately dereference mpHost on the next line
(enet_socket_set_option) without checking. This would crash.

NOTE: The original audit also flagged NetworkDiscovery.cpp, but that file
uses raw Winsock sockets, not ENet. No enet_host_create() calls exist there.
Only two call sites need fixing.

--- Change 1 — Client.cpp: guard enet_host_create ---

File: Engine/Source/Network/Client/Client.cpp

After line 19 (mpHost = enet_host_create(...)), add a null check that returns
early. The constructor cannot return failure, so set mpHost to nullptr and
let Poll()'s existing null check (line 70) handle the no-host state:

  BEFORE (lines 19-22):
    mpHost = enet_host_create(nullptr, 1, NetworkManager::kuiChannelCount, 0, 0);
    // 1MB send/receive buffers to handle bursty packet traffic
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_SNDBUF, 1024 * 1024);
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_RCVBUF, 1024 * 1024);

  AFTER:
    mpHost = enet_host_create(nullptr, 1, NetworkManager::kuiChannelCount, 0, 0);
    if (mpHost == nullptr)
    {
        Log(kLogNetwork, "Client::Client enet_host_create failed");
        return;
    }
    // 1MB send/receive buffers to handle bursty packet traffic
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_SNDBUF, 1024 * 1024);
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_RCVBUF, 1024 * 1024);

--- Change 2 — Server.cpp: guard enet_host_create ---

File: Engine/Source/Network/Server/Server.cpp

Same pattern. After line 21, add null check and return early. Poll() already
checks mpHost == nullptr on line 48.

  BEFORE (lines 21-24):
    mpHost = enet_host_create(&address, 64, NetworkManager::kuiChannelCount, 0, 0);
    // 1MB send/receive buffers to handle bursty packet dispatches
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_SNDBUF, 1024 * 1024);
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_RCVBUF, 1024 * 1024);

  AFTER:
    mpHost = enet_host_create(&address, 64, NetworkManager::kuiChannelCount, 0, 0);
    if (mpHost == nullptr)
    {
        Log(kLogNetwork, "Server::Server enet_host_create failed");
        return;
    }
    // 1MB send/receive buffers to handle bursty packet dispatches
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_SNDBUF, 1024 * 1024);
    enet_socket_set_option(mpHost->socket, ENET_SOCKOPT_RCVBUF, 1024 * 1024);


=== Part B: Workbuffer Push/Pop RAII Guard (LOW PRIORITY) ===

Status: NOT FIXING. The audit flagged that if enet_packet_create or
enet_peer_send fails between Push() and Pop(), the workbuffer is left in a
corrupted state.

Validation: This is technically true but not worth fixing because:
  1. enet_packet_create only fails on malloc failure (process is already dying)
  2. enet_peer_send returns an error code but never throws; the packet is
     either queued or silently dropped by ENet
  3. Every send function in ClientSend.cpp and ServerSend.cpp follows the
     same Push/work/Pop pattern, and none of the intermediate calls can
     throw or skip Pop()
  4. Adding a ScopedWorkbufferGuard would require new infrastructure for
     zero practical benefit

No changes needed.


=== Audit Finding Corrections ===

T1-4 (ENet Packet Memory Leak in Simulation Path): INVALID.
  The original audit claimed packets queued via EnqueueOrDrop() are never
  destroyed. Reading NetworkSimulation.h shows this is false:
    - Unreliable packets: data is copied via .assign(), then
      enet_packet_destroy() is called on line 107
    - Dropped packets: enet_packet_destroy() is called on line 94
    - Reliable packets: HandleReliable is called, then
      enet_packet_destroy() is called on line 112
  All three code paths correctly destroy the original ENet packet after
  copying or processing. There is no leak.

T1-5 (Missing enet_host_create Error Checks): PARTIALLY VALID.
  The audit correctly identified Client.cpp:19 and Server.cpp:21 as missing
  null checks. However, it incorrectly listed NetworkDiscovery.cpp lines
  11, 34, and 46 -- that file uses raw Winsock sockets (socket(), bind(),
  etc.), not ENet. Only 2 of the 5 claimed call sites are real.

T4-4 (Workbuffer Push/Pop Not RAII-Guarded): INVALID (practical).
  Technically true but not actionable. See Part B above.
