Client Performance Plan
=======================

Validated findings from the network client performance audit. Each item was
verified against the source code and assessed for impact, correctness, and
implementation risk.

------------------------------------------------------------------------
ACCEPTED ITEMS
------------------------------------------------------------------------

[P1] Linear Subscription Lookup in BuildSubscriptionQueue
  File: Engine/Source/Network/Client/ClientSessionBase.cpp:127-149

  Issue (confirmed): For each desired coord, the inner loop iterates all coord
  slots to check if already subscribed. This is O(desired * slots). With 5
  slots and 4 desired coords this is 20 iterations -- trivially cheap today.

  However, the fix is simple, low-risk, and improves code clarity. The slot
  count is a constant set by kiDesiredCoordSlots (currently 5) and desired
  coords is similarly small (4), so the real motivation is cleaner code rather
  than measurable perf.

  Fix: Build a small local array of active subscribed coords from slots first,
  then check membership against that array. Avoids repeated state checks.

  Implementation:
  1. In BuildSubscriptionQueue(), before the desired-coords loop, build a local
     std::array or stack buffer of subscribed GridCoords from active slots
  2. Replace the inner slot loop with a simple std::ranges::contains on the
     pre-built array

  Risk: Low. Pure local refactor, no protocol or state changes.

------------------------------------------------------------------------

[P2] Redundant Map Lookups in ApplyReceivedUpdatesBase
  File: Engine/Source/Network/Client/ClientSessionBase.cpp:197-205

  Issue (confirmed): Lines 197-205 call .contains() then .insert_or_assign()
  on the same key in serverUpdates (a std::map). Each operation is an O(log n)
  tree traversal, so this performs two lookups when one suffices.

  Fix: Replace the contains() + insert_or_assign() pair with try_emplace().
  try_emplace() does a single lookup: it inserts if the key is absent and
  does nothing if present -- which is exactly the desired behavior (skip
  duplicate ticks).

  Implementation:
  1. Replace:
       if (!rSub.serverUpdates.contains(rUpdate.iTick))
       {
           rSub.serverUpdates.insert_or_assign(rUpdate.iTick, ...);
           bHasNewData = true;
       }
     With:
       auto [it, bInserted] = rSub.serverUpdates.try_emplace(rUpdate.iTick, ...);
       if (bInserted)
       {
           bHasNewData = true;
       }

  Risk: Low. Single-line behavioral equivalent, no side effects.

DISCARDED ITEMS

[T3-4] Subscription Queue Limited to One-at-a-Time
  File: Engine/Source/Network/Client/ClientSessionBase.cpp:76-98

  Issue: Only one subscription processed per frame, gated until kActive.

  Verdict: DISCARDED -- intentional design, not a bug.

  The one-at-a-time gate exists because the client picks a local slot
  (kSubscribing) and then the server assigns a potentially different slot
  index via SubscribeAccept. The ClearSubscribingPlaceholder() logic in
  ClientReceive.cpp handles remapping when the server assigns a different
  slot. Allowing multiple concurrent in-flight subscriptions would require
  tracking multiple kSubscribing placeholders simultaneously, and the
  full-state arrival can race with the accept (arriving on different ENet
  channels). The existing code already handles the single-slot race case
  with careful ordering checks.

  With only 4 desired coords (human cell + 3 quadrant neighbors) and
  subscriptions happening at grid transitions (infrequent), the 100-300ms
  delay estimate is reasonable but only occurs during initial connection or
  grid transitions. The complexity of managing multiple in-flight subscribe
  state machines is not justified for a < 1 second one-time cost.

[T3-7] ACK Stream Iterates All 64 Slots (Most Inactive)
  File: Engine/Source/Network/Client/ClientSend.cpp:10-58

  Issue: SendAck iterates all slots even though typically few are active.

  Verdict: DISCARDED -- finding is factually wrong about "64 slots."

  The actual slot count is 5 (kiDesiredCoordSlots = 5 in Game.h), not 64.
  The code iterates mCoordSlots which is sized to iCoordSlots (5). Two
  passes over 5 elements is 10 iterations total. This is negligible and
  the code is already correct: it writes uiAckSlotCount first, then only
  includes active slots in the packet (variable-length). The server reads
  exactly uiAckSlotCount entries. No change needed.

[T3-8] Full-State Decompression Blocks Main Thread
  File: Engine/Source/Network/Client/ClientReceive.cpp:11-29, 43-105

  Issue: DecompressAndReadFrame() does LZ4 decompression on main thread.

  Verdict: DISCARDED -- architectural change out of scope.

  Full-state decompression happens once per coord subscription (at grid
  transitions or initial connection), not every frame. Moving it to a
  worker thread would require a deferred processing queue, synchronization
  for the mCoordSlots state machine, and handling the race with delta
  updates arriving on the slot before full state is processed. The
  one-time cost of decompressing a single frame is small relative to the
  complexity of async decompression with correct ordering guarantees.

[T3-10] Reconciliation Workspace Pre-Allocated for All Coords
  File: Projects/BrokenEngineSandbox/Source/Network/ClientReconciler.h:38-39

  Issue: CoordReconcileWork always has replayWorkspace/replayStack vectors.

  Verdict: DISCARDED -- not a real allocation issue.

  replayWorkspace and replayStack are std::vectors that are default-
  constructed empty (no heap allocation until push_back). They only
  allocate when the coord actually needs full replay (non-fast-path).
  For CRC fast-path coords, these vectors are never populated. The
  finding misunderstands how std::vector default construction works --
  an empty vector has no heap allocation.

[T5-7] Snapshot Ring Buffer Sized to 1 Second (May Be Tight)
  File: Engine/Source/Network/Client/ClientSessionBase.cpp:267-297

  Issue: Ring buffer is kiTickRate (32) frames, which is 1 second.

  Verdict: DISCARDED -- no evidence of a real problem.

  The ring buffer stores extrapolation snapshots between reconciliation
  cycles. PrepareExtrapolationTick (line 278-290) already handles the
  full case: when iSnapshotCount >= kiTickRate and iConfirmedOffset > 0,
  it advances the head (discarding oldest confirmed snapshot). If
  iConfirmedOffset == 0, it simply stops recording. This means the ring
  gracefully degrades rather than breaking.

  A 1-second buffer at 32Hz means the client can extrapolate 32 ticks
  ahead of the last confirmed state. Given the clock correction system
  targets the client to be only RTT/2 ticks ahead (typically 1-4 ticks),
  32 ticks is generous. The buffer would only fill if reconciliation
  stalled for a full second, which would trigger the clock error
  disconnect threshold first (kiClockErrorDisconnectThreshold).
