Network Metrics & Adaptive Buffering
=====================================

GOAL: Measure packet loss rate and interarrival jitter from existing data, then use
jitter to adaptively throttle ReconcileReplayCoord() — hold updates longer under
high jitter, process promptly under low jitter.

PREREQUISITES: RTT is ALREADY DONE. Client embeds nanosecond timestamp in SendAck()
(ClientSend.cpp:45), server echoes it in kServerCoordUpdate/kServerCoordResend,
client computes RTT in ServerCoordUpdateOrResend() (ClientReceive.cpp:117-127) via
mSmoothedPipelineRttUs (Smoothed<int64_t> ring buffer).

=====================================
PHASE 1: Network Metrics (Engine Layer)
=====================================

--- 1A. Packet Loss Rate from ACK Bitfield ---

The ACK bitfield already tracks gaps. AckState (NetworkProtocol.h:50-55) has
iAckFloor and uiReceivedBitfield. TrackReceivedTick() (Client.cpp:193-233) sets
bits for received frames and advances the floor past contiguous runs.

Packet loss = ratio of gaps seen to total frames tracked. Track this with two
running counters per Client (not per slot — aggregate across all active slots).

FILE: Engine/Source/Network/Client/Client.cpp
  In TrackReceivedTick() (line 193), after the floor-advance while loop (line 227-231):
    Count how many floor advances happened (= contiguous bits consumed + 1 for the
    frame that triggered it). Before the while loop, record iOldFloor = rAck.iAckFloor.
    After the while loop, iAdvanced = rAck.iAckFloor - iOldFloor. Each advance
    represents one frame confirmed as received. The current frame that triggered the
    advance is also received. But any bits that were NOT set in the consumed range
    represent gaps. Since the floor only advances past contiguous 1-bits, all advances
    are received frames.

    Simpler approach: just count receives vs expected:
    - Every call to TrackReceivedTick = 1 received frame -> ++miPacketLossReceived
    - Before the floor-advance loop, record iOldFloor. After, compute
      iAdvanced = rAck.iAckFloor - iOldFloor. miPacketLossReceived already counts
      the current frame. The iAdvanced frames moved past the floor are confirmed
      received. No gap counting needed at advance time.
    - Actually, the simplest correct approach: when a frame arrives with iBitIndex > 0,
      that means frames between old floor and this frame's tick may be missing.
      But they might arrive later (reordered). So loss is best measured over a window.

    Final approach (simple and correct):
    - On each call to TrackReceivedTick: ++miPacketLossReceived
    - On each floor advance (inside the while loop): count the advance.
      After the while loop: iAdvanced = rAck.iAckFloor - iOldFloor.
      miPacketLossGaps stays unchanged (advances = received, no gap).
    - BUT: frames that are NEVER received get pushed out of the 64-bit window.
      When iBitIndex >= 63, the old unset bits represent lost frames.

    {

        if (iExpected <= 0) return 0.0f;
        int64_t iReceived = mFramesReceived.Get();
        int64_t iLost = iExpected - iReceived;
        if (iLost <= 0) return 0.0f;
        return static_cast<float>(iLost) * 100.0f / static_cast<float>(iExpected);
    }


--- 1B. Interarrival Jitter Tracking ---

Track jitter of server coord updates using RFC 3550 EWMA formula. Measure the
variation in arrival spacing of kServerCoordUpdate packets (not resends).

Jitter = EWMA of |actual_interval - expected_interval|
Expected interval = one server tick (constant, = kTickNs from game constants).
Actual interval = time between consecutive ServerCoordUpdateOrResend() calls
for kServerCoordUpdate (bProcessRtt == true).

=====================================
PHASE 2: Adaptive Buffering in ReconcileReplayCoord()
=====================================

ReconcileReplayCoord() (ReconcileReplay.cpp:359-436) already throttles replay:
  - Line 362: iMaxReplay = (iMaxConsecutive - rWork.iConfirmedTick + 1) / 2
  - This replays at most HALF of available consecutive updates per pass.

The adaptation: under high jitter, replay FEWER frames per pass (hold updates
longer so late packets can fill gaps). Under low jitter, replay MORE (up to
the existing half-limit or even all of them).

The jitter value needs to flow from engine::Client -> game::ClientSession ->
ReconcileContext -> ReconcileReplayCoord().

  With:
    // Adaptive buffering: high jitter -> replay fewer, low jitter -> replay more
    int64_t iAvailable = iMaxConsecutive - rWork.iConfirmedTick + 1;
    int64_t iMaxReplay = iAvailable / 2;  // default: half
    constexpr int64_t kiLowJitterThresholdUs = 2000;    // 2ms
    constexpr int64_t kiHighJitterThresholdUs = 8000;   // 8ms
    int64_t iJitterUs = rReconcileContext.iJitterUs;
    if (iJitterUs <= kiLowJitterThresholdUs)
    {
        iMaxReplay = iAvailable;  // low jitter: process all available
    }
    else if (iJitterUs >= kiHighJitterThresholdUs)
    {
        iMaxReplay = std::max(iAvailable / 4, 1LL);  // high jitter: quarter
    }
    // else: medium jitter keeps default half

  is accessible via rReconcileContext.iJitterUs.
