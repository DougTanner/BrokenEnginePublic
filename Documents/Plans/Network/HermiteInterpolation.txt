Hermite Spline Interpolation for Render Smoothing
==================================================
Priority: LOW - Only implement if cornering artifacts are observed during gameplay
Status: Ready for implementation

PROBLEM
-------
Current render interpolation uses linear velocity integration:
  position = previousPosition + velocity * deltaTime

This produces straight-line segments between frames. When entities change direction
(spaceships turning, missiles tracking), the linear approximation creates visible
"corner" artifacts at frame boundaries.

SOLUTION
--------
Replace linear integration with cubic Hermite spline interpolation in each
collection's Interpolate::Update() method. Hermite uses position AND velocity at
both endpoints (previous frame and current frame) to produce smooth curves:

  P(t) = (2t^3 - 3t^2 + 1)*P0 + (t^3 - 2t^2 + t)*V0*dt + (-2t^3 + 3t^2)*P1 + (t^3 - t^2)*V1*dt

Where:
  P0 = previous position, V0 = previous velocity
  P1 = current position (from the physics tick), V1 = current velocity
  t  = normalized time (fDeltaTime / kfDeltaTime), clamped to [0,1]
  dt = kfDeltaTime (fixed timestep interval)

KEY INSIGHT: No new data structures needed. The rPreviousFrame parameter already
provides access to both previous-frame positions AND previous-frame velocities via
the PostRender collections. The "current" endpoint (P1, V1) comes from the physics
tick result that the interpolation is building on top of.

ARCHITECTURE
------------
The interpolation system works as follows:

1. GameBase::Render() (Engine/Source/GameBase.cpp, line 241) computes:
     float fDeltaTime = max(0.0f, NanosecondsToFloatSeconds(mTimeStep.mTickRemainderNs))
   This is the sub-step remainder between the last physics tick and the render time.

2. FrameInterpolate::Update() (Projects/.../Frame/Frame.cpp, line 84) receives fDeltaTime,
   stores it in rCurrent.fDeltaTime (via FrameInterpolateBase::Update at
   Engine/Source/Frame/FrameBase.cpp, line 243), then dispatches to per-collection Update()
   methods via ForEachInterpolateUpdate (Engine/Source/Frame/FrameUtils.h, line 37-40).

3. Each collection's Update() reads from rPreviousFrame and writes interpolated state
   into rCurrent for the renderer to consume.

Hermite interpolation applies to POSITION ONLY. Direction/rotation continues using
the existing linear/slerp methods.

COLLECTIONS REQUIRING CHANGES
------------------------------
Only game-level collections that do velocity-based position interpolation need changes.
Engine-level collections (Explosions, Pushers, etc.) either don't move or use different
interpolation strategies.

1. SpaceshipsInterpolate::Update()
   File: Projects/BrokenEngineSandbox/Source/Frame/Collections/Spaceships/SpaceshipsUpdate.cpp
   Line 103: void SpaceshipsInterpolate::Update(...)

   Current (line 136):
     vecPosition = XMVectorMultiplyAdd(XMVectorReplicate(fDeltaTime), rPreviousPostRender.pVecVelocities[i], vecPosition);

   Data available:
     P0 = rPrevious.pVecPositions[i]                    (line 124)
     V0 = rPreviousPostRender.pVecVelocities[i]         (line 136, already accessed)
     P1 = already computed by physics tick, stored in rCurrentFrameInterpolate.pSpaceships->pVecPositions[i]
          BUT this is the OUTPUT being written, so P1 must come from the physics tick's
          result. Since AllocateAndCopy runs first, rCurrent starts as a copy of rPrevious.
          The "true next position" is: P0 + V0 * kfDeltaTime (one full tick step).
     V1 = current velocity is computed in SpaceshipsPostRender::Update() which runs AFTER
          interpolation. For render interpolation, V1 is not yet available.

   APPROACH: Use the available data. For render interpolation (sub-step remainder),
   we have P0, V0, and can compute P1 = P0 + V0 * kfDeltaTime. For V1, we approximate
   using V0 (velocity doesn't change much in one sub-step). This simplifies the Hermite
   to a position-only curve with matching tangents at endpoints:

     t = fDeltaTime / kfDeltaTime  (clamped [0,1])
     P1 = P0 + V0 * kfDeltaTime
     // With V0 == V1 approximation, Hermite reduces to:
     // P(t) = (2t^3 - 3t^2 + 1)*P0 + (t^3 - 2t^2 + t)*V0*dt + (-2t^3 + 3t^2)*P1 + (t^3 - t^2)*V0*dt

   WAIT - this simplifies further. If V0 == V1 and P1 = P0 + V0*dt, the Hermite
   actually reduces to linear interpolation. The benefit of Hermite comes from V0 != V1.

   REVISED APPROACH: We need TWO frames of velocity data. The previous frame's
   PostRender has the velocity that PRODUCED the current position (V0). The current
   frame's PostRender has the velocity that WILL produce the next position (V1). But
   SpaceshipsPostRender::Update() runs AFTER interpolation in the tick pipeline.

   However, for the RENDER interpolation path (GameBase::Render), we are interpolating
   between TWO ALREADY-COMPUTED physics frames. The "rPreviousFrame" passed to Update()
   is the LATEST completed frame. So:
     - The frame BEFORE rPreviousFrame had velocity V_prev
     - rPreviousFrame has velocity V_current (in postRender.pSpaceships->pVecVelocities)

   We need access to the frame before rPreviousFrame. This is NOT available in the
   current Update() signature.

   SIMPLEST VIABLE APPROACH: Use velocity change within the current frame to estimate
   curvature. Between the AllocateAndCopy'd previous state and the PostRender-computed
   state, we have two velocity snapshots. But at interpolation time, PostRender hasn't
   run yet for the render interpolate.

   FINAL APPROACH (practical):
   The render interpolation copies from the LATEST physics frame and advances by
   fDeltaTime (the sub-step remainder, typically 0-15ms at 64Hz). The "previous frame"
   in this context IS a fully computed frame with both interpolate and postRender data.

   Actually, re-reading GameBase::Render() (line 272-277):
     const Frame& rFrame = RenderFrame(rCoord);  // Latest completed frame
     AllocateAndCopy(renderInterpolate, rFrame.interpolate);  // Copy latest frame
     Update(renderInterpolate, rFrame, fDeltaTime);  // Advance by remainder

   So rFrame IS a complete frame. rPreviousFrame in Update() IS this complete frame.
   The positions in rPrevious are the latest physics positions, and the velocities in
   rPreviousPostRender are the latest physics velocities.

   For Hermite, we need the velocity at the START of the interval (V0) and the velocity
   at the END (V1). But we only have one velocity snapshot (the latest frame's velocity).

   CONCLUSION: True Hermite requires two frames of data. The simplest change that
   provides curvature-aware smoothing WITHOUT architectural changes is to use the
   velocity and the ACCELERATION (velocity change) to estimate curvature. But
   acceleration isn't stored either.

   PRACTICAL IMPLEMENTATION: Add a second velocity parameter to the interpolation.
   Since the Frame struct contains BOTH interpolate and postRender from the SAME tick,
   and the PREVIOUS tick's data is what we copied from, we can access two consecutive
   velocity snapshots IF we store the previous velocity. But this adds a new SOA field.

   SIMPLEST HERMITE THAT WORKS:
   Store nothing new. Use the fact that during a PHYSICS TICK, the interpolation Update()
   also runs (with fDeltaTime = kfDeltaTime, a full tick). In that case, the frame
   before rPreviousFrame had different positions. The position CHANGE over the last tick
   implicitly encodes the previous velocity:

     V0_implicit = (rPrevious.position - position_two_frames_ago) / kfDeltaTime

   But position_two_frames_ago isn't available either.

   ============================================================
   REVISED DESIGN: Add pVecPreviousVelocities to PostRender
   ============================================================

   The cleanest approach is to store the previous tick's velocity alongside the current
   velocity in each PostRender collection. This is one XMVECTOR* per entity per
   collection -- minimal memory overhead. Updated once per tick in PostRender::Update()
   by copying the previous frame's velocity before computing the new one.

   With V_prev (velocity that moved entity TO current position) and V_current (velocity
   that will move entity FROM current position), Hermite interpolation becomes:

     P0 = rPrevious.pVecPositions[i]
     V0 = rPreviousPostRender.pVecPreviousVelocities[i]  // velocity of prior tick
     P1 = P0 + V0 * kfDeltaTime  // could also be: the actual next-tick position
     V1 = rPreviousPostRender.pVecVelocities[i]  // current tick velocity
     t  = fDeltaTime / kfDeltaTime

   But wait -- this still only helps when interpolating a full tick. For the render
   sub-step, we're extrapolating a FRACTION of a tick from the latest known state.
   The Hermite curve from P0 to P1 covers one full tick. We evaluate at t < 1.

   This DOES help: if V0 and V1 differ (entity turning), the Hermite curve will
   follow the turn arc instead of a straight line, even for sub-step fractions.

### 1. Common utility: HermitePosition helper
File: Common/Math.h (or inline in each Update)

Add a helper function (or just inline the math):

  inline XMVECTOR XM_CALLCONV HermitePosition(
      FXMVECTOR vecP0, FXMVECTOR vecV0,
      FXMVECTOR vecP1, GXMVECTOR vecV1,
      float fT, float fDT)
  {
      float t2 = fT * fT;
      float t3 = t2 * fT;
      float h00 = 2.0f * t3 - 3.0f * t2 + 1.0f;
      float h10 = t3 - 2.0f * t2 + fT;
      float h01 = -2.0f * t3 + 3.0f * t2;
      float h11 = t3 - t2;
      XMVECTOR vecResult = XMVectorScale(vecP0, h00);
      vecResult = XMVectorMultiplyAdd(XMVectorScale(vecV0, fDT), XMVectorReplicate(h10), vecResult);
      vecResult = XMVectorMultiplyAdd(vecP1, XMVectorReplicate(h01), vecResult);
      vecResult = XMVectorMultiplyAdd(XMVectorScale(vecV1, fDT), XMVectorReplicate(h11), vecResult);
      return vecResult;
  }

RISK ASSESSMENT
---------------
- LOW RISK: Changes are isolated to render interpolation (client-only visual path).
  Physics tick positions are unchanged. Server determinism is unaffected since
  pVecPreviousVelocities is a PostRender field (not in ServerCrc).
- The pVecPreviousVelocities field adds ~16 bytes per entity per collection to memory.
  With typical entity counts (<100 spaceships, <8 players, <50 missiles), this is
  negligible.
- Edge case: First frame after spawn has no "previous velocity." Initialize
  pVecPreviousVelocities to pVecVelocities in the Spawn() method so the first
  interpolation degrades to linear (V0 == V1).
