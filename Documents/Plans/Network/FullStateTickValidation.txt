# Full State Tick Validation

## Context

Pending full states (resync frames sent by the server) are accepted without
validating their tick against the current confirmed state. This creates three
problems identified in the reconcile audit (E6, E7, E8, F8):

1. A full state with a tick far in the past (e.g., confirmed=100, fullState=50)
   is injected at rollback time as the replay base. The simulation then replays
   from tick 50 to reach tick 101, producing incorrect results and triggering a
   CRC desync. The desync is caught, not silent, but causes a wasteful
   resync round-trip.

2. A full state with a tick beyond the available server updates is never
   injected during replay (the injection check at ReconcileReplay.cpp:372
   requires an exact tick match). The unconsumed pendingFullState is not
   written back in ApplyCoordWriteback -- it is lost when mpContext is reset.

3. No validation that the server-sent full state tick is reasonable. A
   corrupted or wrong-tick state is accepted blindly by ApplyReceivedFullStates,
   setting iConfirmedTick to the bad tick and triggering repeat desyncs.

4. No assertion that the injected full state Frame's internal tick
   (interpolate.iTick) matches the declared pendingFullState->iTick.

## Changes

### 1. ClientSession.cpp - ApplyReceivedFullStates: reject stale full states

In the `else` branch (coord already has confirmed state, line 253-261), add a
check that rejects full states with a tick at or before iConfirmedTick. These
are stale -- the client has already confirmed past that tick, so injecting
them would produce a wrong replay base.

Location: ClientSession.cpp, inside the `else` block at line 253

Before:
```
		else
		{
			// Coord already has confirmed state: store as pending for reconcile injection
			rSub.pendingFullState = engine::CoordFrames::PendingFullState {
				.iTick = iTick,
				.pFrame = std::move(rFullState.pFrame),
			};

			mpReconciler->SetHasNewData();
		}
```

After:
```
		else
		{
			// Reject stale full states: tick must be after confirmed tick
			if (iTick <= rSub.iConfirmedTick)
			{
				Log(kLogNetwork, "ApplyReceivedFullStates Rejected stale full state Coord: ({},{}) FullStateTick: {} ConfirmedTick: {}", coord.x, coord.y, iTick, rSub.iConfirmedTick);
				continue;
			}

			// Coord already has confirmed state: store as pending for reconcile injection
			rSub.pendingFullState = engine::CoordFrames::PendingFullState {
				.iTick = iTick,
				.pFrame = std::move(rFullState.pFrame),
			};

			mpReconciler->SetHasNewData();
		}
```

Rationale: Rejecting at receive time (rather than reconcile time) is
preferred because it avoids moving the frame into the reconcile context
only to discard it. The server should never send a full state for a tick
the client has already confirmed past, so this is a defensive check.


### 2. ClientReconciler.cpp - ApplyCoordWriteback: preserve unconsumed pending full state

If the reconciler did not consume the pending full state (tick was beyond the
replay range), write it back to CoordFrames so it survives for the next
reconcile pass.

Location: ClientReconciler.cpp, at the end of ApplyCoordWriteback (after the
server updates merge loop, after line 184)

Add:
```
	// Preserve unconsumed pending full state for next reconcile pass
	if (rWork.pendingFullState.has_value())
	{
		rSub.pendingFullState = std::move(rWork.pendingFullState);
	}
```

Rationale: The current code moves pendingFullState into the work item at
Kick time (line 100) and resets it on CoordFrames (line 109). If the
full state tick is beyond the replay range, ReconcileInjectPendingFullState
is never called, and the pending state is silently lost when mpContext is
reset. Writing it back ensures it will be available for the next reconcile
pass when sufficient server updates arrive.

This writeback must also be added to the desync path in ApplyResult
(line 206-229), alongside the existing server update restore.

Location: ClientReconciler.cpp, in the desync restore loop, after the
server updates restore (after line 224)

Add:
```
			// Preserve unconsumed pending full state
			if (rWork.pendingFullState.has_value())
			{
				rSub.pendingFullState = std::move(rWork.pendingFullState);
			}
```


### 3. ReconcileReplay.cpp - ReconcileInjectPendingFullState: assert tick match

Add an ASSERT verifying the full state Frame's internal tick matches the
declared pendingFullState tick. This catches serialization or bookkeeping
errors early.

Location: ReconcileReplay.cpp, at the top of ReconcileInjectPendingFullState
(line 199), before the slot assignment

Add:
```
	ASSERT(rWork.pendingFullState->pFrame->interpolate.iTick == rWork.pendingFullState->iTick);
```

Rationale: An ASSERT is sufficient here (not a runtime check) because:
- The tick is set by RunFrameTick (FrameTick.cpp:16) on the server before
  serialization and deserialized on the client, so a mismatch indicates a
  genuine bug, not a recoverable condition.
- The full state is already CRC-validated by the server before sending.
- If this fires, the correct action is to investigate the serialization
  path, not to silently discard the frame.


### 4. ReconcileReplay.cpp - ReconcileCoord: clamp stale full state injection

The check at line 463 injects a pending full state when
`pendingFullState->iTick <= confirmedTick`. If the tick is much earlier than
confirmedTick (e.g., tick 50 vs confirmed 100), this replaces the confirmed
frame with a far-past state, producing incorrect replay results.

Change the condition to only inject when the tick exactly equals
confirmedTick. Full states with a tick before confirmedTick should have
been rejected at receive time (Change 1), but as a defensive measure the
reconcile path should also reject them.

Location: ReconcileReplay.cpp, line 462-468

Before:
```
	// Inject pending full state at or before confirmed frame
	if (rWork.pendingFullState.has_value() && rWork.pendingFullState->iTick <= rWork.iConfirmedTick)
	{
		ReconcileInjectPendingFullState(rReconcileContext, rWork);
		fTime = rWork.replayStack[0]->interpolate.fCurrentTime;
		Log(kLogNetwork, "ReconcileCoord Injected pending full state Coord: ({},{}) AtTick: {}", rWork.coord.x, rWork.coord.y, rWork.iConfirmedTick);
	}
```

After:
```
	// Inject pending full state at confirmed frame (stale states rejected at receive time)
	if (rWork.pendingFullState.has_value() && rWork.pendingFullState->iTick == rWork.iConfirmedTick)
	{
		ReconcileInjectPendingFullState(rReconcileContext, rWork);
		fTime = rWork.replayStack[0]->interpolate.fCurrentTime;
		Log(kLogNetwork, "ReconcileCoord Injected pending full state Coord: ({},{}) AtTick: {}", rWork.coord.x, rWork.coord.y, rWork.iConfirmedTick);
	}
	else if (rWork.pendingFullState.has_value() && rWork.pendingFullState->iTick < rWork.iConfirmedTick)
	{
		Log(kLogNetwork, "ReconcileCoord Discarded stale pending full state Coord: ({},{}) FullStateTick: {} ConfirmedTick: {}", rWork.coord.x, rWork.coord.y, rWork.pendingFullState->iTick, rWork.iConfirmedTick);
		rWork.pendingFullState.reset();
	}
```

Rationale: Full states with tick < confirmedTick are stale. Change 1
rejects them at receive time, but the confirmed tick can also advance
between receive and reconcile (via CRC fast path in a prior reconcile
pass). The defensive discard here catches that case. Full states with
tick > confirmedTick are preserved for the next pass via Change 2.
