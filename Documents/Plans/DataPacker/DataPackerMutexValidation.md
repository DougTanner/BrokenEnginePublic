# Validate the single-instance mutex before running commands

## Context

Verified by `/external-deep-analysis` over `DataPacker/Source` (baseline `3cb5e9a6`): `main` creates the named single-instance mutex and handles failure only with `__assume(hMutex != nullptr)` (`DataPacker/Source/Main.cpp:544-545`), and the already-running path calls `WaitForSingleObject` without inspecting its result (`:548-552`). `__assume` performs no runtime check, and `CreateMutex` fails (returns null) for example when the name collides with a different kernel-object type. Root `AGENTS.md` requires validating OS API results. After either unchecked failure, two DataPacker processes can reach the shared `%LOCALAPPDATA%` caches and output publication concurrently — the exact hazard the mutex exists to prevent (`DataPacker/Source/AGENTS.md`, single-instance mutex).

## Design

Failure-path-only: if `CreateMutex` returns null, or the wait does not return an owned/abandoned success result, report through the existing diagnostic reporter and exit with failure before any CLI command, export, or materialization runs. Successful and already-running executions keep the existing RAII release/close ownership, behavior, and generated bytes.

## Risk tier and invariants

Expected Change Workflow Tier 2. Trigger: scoped tool behavior at an OS trust boundary; no serialization or layout exposure. Invariants: normal and already-running runs behave identically and produce identical bytes; the failure exit runs before any cache or output access.

## Acceptance criteria

- Forced mutex-creation and wait failures terminate with a diagnostic before any export or materialization work.
- Normal single- and second-instance runs are unchanged.
