# Per-Cell Elevation Grid for Fast GlobalElevation Lookup

## Context

`engine::IslandTerrain::GlobalElevation` profiled at ~13% CPU on the server
(`SpaceshipsPostRender::AvoidTerrain → ComputeTerrainAvoidance → GlobalElevation`).
It is **not** iterating all islands — it looks up the query point's cell in
`game::gpGame->mCoordFrames` and walks that cell's placement list. The cost exploded
after the island-chain work (`8x4 Islands`, `Island chains`) raised per-cell island
counts to as many as ~108. The inner loop is expensive per island: it recomputes
`std::cos(-rotation)` / `std::sin(-rotation)` (two transcendentals, even though rotation
is constant per placement) and does a hash lookup `mIslands.at(crc)` *before* the cheap
footprint reject. It is called ~13×/spaceship/frame (8 from `ComputeTerrainAvoidance`,
5 from `ApplyTerrainBounce`→`GlobalNormal`'s 4 taps) × up to 16 ships × active cells.

There is no precomputed CPU lookup today. The fix: precompute a per-cell elevation grid
once per cell (the GPU already runs an analogous elevation prepass), and make
`GlobalElevation` an O(1) nearest-texel grid lookup. Client and server each build the
grid independently from the deterministic placements + shared island heightmaps — no
network traffic. Outcome: the AI terrain hot path drops from O(islands-per-cell) with
trig+hash to a single array read.

## Approach

A `1024×1024` float grid per cell (`900×900` units → ~0.88 unit / sub-meter spacing,
~4 MB/cell). Stored in `FrameStaticData::elevationGrid` (`mutable`), built lazily at
the top of each cell's `RunFrameTick` and max-blended across all islands.

**Cell-locality (self-contained frames)**: the sim query takes the current cell's
`FrameStaticData` explicitly (mirroring `NavQueryDirection`'s `const NavData&`) and
**never** reads neighbor cells or `gpGame->mCoordFrames`. This honors the Frame
Purity Constraint, removes the hash lookup from the hot path, and makes the lazy
in-tick build trivially race-free (only that worker reads its own grid). Out-of-cell
sample positions return `mfSeaFloorElevation`. Render code (engine client
`ProjectToBaseHeight`, not Frame code) keeps a separate position-based overload that
iterates immutable `mCoordFrames` islands — never touches the grid, so it never races
the tick-time build.

Quantizing queries to grid-cell centers (vs. exact point today) shifts values slightly
→ **`Frame::kiVersion` bumps** (old saves/replays invalidate). Sub-meter spacing makes
the gameplay effect negligible.

### Determinism invariants (load-bearing)
- Both client and server build bit-identical grids: same deterministic placements (same
  iteration order), same shared heightmaps, `/fp:strict` math. Grid is **not** in the
  CRC and **not** serialized — purely local derived data (like `navData`).
- All sim/CRC-affecting elevation calls go through the cell-local overload, take their
  cell's grid as an explicit parameter, and only ever read their own worker's
  `FrameStaticData`. No cross-coord reads under `Dispatch()`.
- The build runs at the very top of `RunFrameTick` (before any phase), so AI/spawn
  callers later in the same tick always see a built grid.

## API shape

```cpp
// Sim path (Frame-tick callers). Cell-local. O(1) nearest grid lookup. Out-of-cell
// positions return mfSeaFloorElevation. Honors the Frame Purity Constraint.
[[nodiscard]] float XM_CALLCONV GlobalElevation(const FrameStaticData& rStaticData, FXMVECTOR vecPosition) const;
[[nodiscard]] XMVECTOR XM_CALLCONV GlobalNormal(const FrameStaticData& rStaticData, FXMVECTOR vecPosition) const;

// Render path (engine client only — ProjectToBaseHeight). Position-based iteration
// over mCoordFrames' immutable islands list. Never touches the per-cell grid, so
// it never races the tick-time build. NOT for Frame tick code.
[[nodiscard]] float XM_CALLCONV GlobalElevation(FXMVECTOR vecPosition) const;
```
