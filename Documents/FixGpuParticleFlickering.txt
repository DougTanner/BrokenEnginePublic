# Fix GPU Particle Flickering

## Context

GPU particles flicker as if not rendering every frame. The issue is specific to particles -- all other rendering is stable.

### Why the existing fence wait doesn't help

The per-framebuffer fence protects CPU->GPU data flow: it ensures the previous use of framebuffer N has completed before the CPU writes new spawn data, uniforms, and host-visible indirect buffers for framebuffer N. All CPU-written resources are per-framebuffer, so this works correctly.

The particle system is different. It has singleton device-local buffers that are written exclusively by GPU compute shaders (not the CPU):
- mLongParticlesStorageBuffer / mSquareParticlesStorageBuffer -- persistent particle state (positions, velocities, allocation bitmask)
- Device-local indirect draw/dispatch buffers in particle Pipeline objects -- written by spawn compute

These are shared across all framebuffers. The intra-frame barriers (spawn->update->render) synchronize correctly within a single frame. But the global CB has zero wait semaphores, so Frame N+1's spawn compute can begin executing on the GPU while Frame N's main CB (particle render) is still reading these same buffers. This is a GPU<->GPU data race that only affects resources written by GPU compute -- which is only particles.

### Why only particles are affected

All other indirect draws use host-visible indirect buffers written by the CPU per-framebuffer -- no cross-frame GPU race. Shadow/terrain textures are fully overwritten each frame, so one-frame-ahead data is visually identical. Particle state is persistent and changes significantly between frames (allocation bitmask, positions, counts), making the race visible as flickering.

## Fix: VkEvent for cross-frame particle synchronization

Use a VkEvent recorded into the pre-recorded command buffers:
- Main CB: vkCmdSetEvent after the main render pass ends (after all particle reads complete)
- Global CB: vkCmdWaitEvents before particle spawn compute, with dstStageMask = COMPUTE_SHADER_BIT

This ensures the previous frame's particle rendering completes before the next frame's particle compute begins. Non-compute work in the global CB (shadow render passes, terrain, etc.) proceeds without waiting.

The event is pre-signaled from the host after recording so the first frame doesn't deadlock.

### Files to modify

Engine/Source/Graphics/Managers/CommandBufferManager.h -- add VkEvent member:

    VkEvent mParticleVkEvent = VK_NULL_HANDLE;

Engine/Source/Graphics/Managers/CommandBufferManager.cpp:

1. Constructor -- create event:

    VkEventCreateInfo vkEventCreateInfo
    {
        .sType = VK_STRUCTURE_TYPE_EVENT_CREATE_INFO,
        .pNext = nullptr,
        .flags = 0,
    };
    CHECK_VK(vkCreateEvent(gpDeviceManager->mVkDevice, &vkEventCreateInfo, nullptr, &mParticleVkEvent));

2. Destructor -- destroy event (before command pool/device cleanup)

3. RecordCommandBuffers() -- pre-signal after recording:

    CHECK_VK(vkSetEvent(gpDeviceManager->mVkDevice, mParticleVkEvent));

4. RecordGlobalCommandBuffer() -- after uniform copy (line 91), before particle spawn (line 93):

    vkCmdWaitEvents(vkCommandBuffer, 1, &mParticleVkEvent,
        VK_PIPELINE_STAGE_ALL_COMMANDS_BIT,
        VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT,
        0, nullptr, 0, nullptr, 0, nullptr);
    vkCmdResetEvent(vkCommandBuffer, mParticleVkEvent, VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT);

5. RecordMainCommandBuffer() -- after render pass ends (line 459), before vkEndCommandBuffer (line 462):

    vkCmdSetEvent(vkCommandBuffer, mParticleVkEvent, VK_PIPELINE_STAGE_ALL_COMMANDS_BIT);

## Why this works

- vkCmdSetEvent cannot be inside a render pass, so it's placed after RecordEndRenderPass -- this covers all particle reads (both particle render draws and particle lighting draws)
- vkCmdWaitEvents with dstStageMask = COMPUTE_SHADER_BIT only stalls compute dispatches; shadow/terrain render passes in the global CB proceed without waiting
- The event reset after the wait ensures the next frame also waits
- Pre-signaling via vkSetEvent from the host before first submission prevents first-frame deadlock
- On device recreation: CommandBufferManager is destroyed (event destroyed) and recreated (new event, re-recorded CBs, re-signaled)

## Verification

1. Run the game with particle effects (explosions, trails) -- flickering should stop
2. Verify other rendering is unaffected (shadows, models, terrain)
3. Check GPU profiler -- particle compute may show slightly higher latency from the event wait, but non-particle global work should be unaffected
