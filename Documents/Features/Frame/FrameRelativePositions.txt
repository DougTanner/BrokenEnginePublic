================================================================================
Frame-Relative Positions
================================================================================

CONTEXT
-------
Currently all object positions in the Frame system are world-absolute. A Frame
at GridCoord {5, 0} stores positions near X=3000. IEEE 754 float precision
degrades as magnitude increases:

    Frames from origin  |  World coord  |  Epsilon       |  Meaning
    1                   |  600          |  0.00007       |  0.07mm - perfect
    10                  |  6,000        |  0.0007        |  0.7mm - fine
    100                 |  60,000       |  0.007         |  7mm - noticeable
    140                 |  84,000       |  0.01          |  1cm - jitter visible
    1,000               |  600,000      |  0.07          |  7cm - broken

At ~100-140 frames from origin, smooth rendering and physics break down.

GOAL
----
Store all collection positions as frame-relative (local to each Frame's
coordinate space). All frames use the coordinate range (0,0) to (width,height),
giving perfect float precision (~0.00007 unit epsilon) regardless of how far
the Frame is from the world origin. GridCoord integers handle the "where in the
world" part with zero precision loss.

DEPENDENCY
----------
Section 6 (Render Merge) requires MergeFramesForRender and OffsetPositions
infrastructure, which does not yet exist. Multi-frame rendering merge must be
built first or as part of this plan. Currently rendering operates directly from
rRenderInterpolates without a merge step.


================================================================================
1. COORDINATE INFRASTRUCTURE
================================================================================

Frame origin: the (minX, minY) corner of the frame's world-space vecArea.
Frame-relative position = world_position - frame_origin.
World position = frame_relative_position + frame_origin.

Frame dimensions are identical for all frames: width=600, height=600.
Derived from the base vecArea scaled by 2x in FramePostRenderBase constructor.

Changes:
  - FramePostRenderBase (Engine/Source/Frame/FrameBase.h, struct at ~line 144)
      Keep vecArea (world-space bounds, needed for terrain queries).
      Add vecLocalArea: frame-relative bounds = (0, height, width, 0) in
      vecArea format (minX=0, maxY=height, maxX=width, minY=0). Identical for
      all frames. Computed once from vecArea dimensions.
      Add vecFrameOrigin: XMVECTOR = (minX, minY, 0, 0) extracted from vecArea.
      Used for local<->world conversion.

  - Frame.h helper functions (Projects/BrokenEngineSandbox/Source/Frame/Frame.h):
      Rename/adjust ComputeFrameBounds() (~line 100) to work with vecLocalArea.
      IsOutOfBounds() (~line 122) and ComputeTransferDelta() (~line 131) use
      vecLocalArea (bounds are 0 to width/height for all frames). No position
      conversion needed since positions are already frame-relative.
      Add inline ToWorld(vecLocal, vecFrameOrigin) = XMVectorAdd.
      Add inline ToLocal(vecWorld, vecFrameOrigin) = XMVectorSubtract.

  - Collision::Collide (Engine/Source/Frame/Collision.cpp)
      SetupZones (~line 188) receives vecLocalArea instead of vecArea. Zone grid
      maps to (0,0)-(w,h).
      FrameTick.cpp (~line 25) passes vecLocalArea instead of vecArea.

  - Collision::GetAreaDamage (Engine/Source/Frame/Collision.cpp)
      Area damage sources store positions. These are frame-relative (from
      missiles in the same frame). Queries use frame-relative positions.
      No conversion needed - all same coordinate space.


================================================================================
2. TRANSFER PIPELINE
================================================================================

When an entity leaves a frame, its position must convert to the destination
frame's coordinate space.

Transfer position math:
  dest_local = src_local - (delta * frame_dimensions)

  Example: entity at X=610 in frame (0,0) (past right edge of 600-wide frame).
  delta = +1, dest frame = (1,0).
  dest_local.x = 610 - (1 * 600) = 10. Entity is 10 units into the new frame.

Files and functions that build TransferRequests (position is already
frame-relative, just needs to be stored as-is in TransferData):
  - Players.cpp:215-263     PlayersPostRender::Transfer()
  - Blasters.cpp            BlastersPostRender::Transfer()
  - Missiles.cpp            MissilesPostRender::Transfer()
  - Spaceships.cpp          SpaceshipsPostRender::Transfer()
  All store frame-relative vecPosition in TransferRequest.data.vecPosition.

IsOutOfBounds / ComputeTransferDelta (Frame.h:122-137):
  These compare position against frame bounds. Change to use vecLocalArea
  (bounds are 0 to width/height for all frames). No position conversion needed
  since positions are already frame-relative.

ServerSession.cpp - Transfer orchestration:
  HarvestTransfers (~line 377-399) orchestrates the pipeline:
    1. CollectTransfers (~line 303-331) - reads transferRequests from each frame,
       computes destination coord = source_coord + (iDeltaX, iDeltaY)
    2. SortTransfersByType (~line 333-342)
    3. SpawnTransfers (~line 344-355) - calls Game::SpawnTransfer for each

  Game.cpp - SpawnTransfer (~line 226-308):
    Routes TransferData to appropriate collection spawn method.
    Change: convert position from source frame-relative to dest frame-relative:
      data.vecPosition -= delta * vecFrameDimensions
    where vecFrameDimensions = (width, height, 0, 0) and delta is (iDeltaX,
    iDeltaY). This is a single XMVectorNegativeMultiplySubtract per transfer.

================================================================================
4. SPAWNING
================================================================================

All spawn positions must be frame-relative.

Player spawn from StatusChange (Players.cpp):
  Currently computes frame center from world-space vecArea:
    fCenterX = (minX + maxX) * 0.5f
    fCenterY = (minY + maxY) * 0.5f
  Change to frame-relative center:
    fCenterX = width * 0.5f
    fCenterY = height * 0.5f

SpawnSingleSpaceship (Frame.cpp:171-223):
  Reads player position (already frame-relative after the change).
  Computes spawn position as offset from player - works as-is in local coords.
  GlobalElevation calls at ~line 201, 206 need world-space conversion (section 3).
  common::InsideArea check at ~line 210 needs adjustment: compare against
  vecLocalArea instead of world vecArea, using the frame-relative position.

Blaster spawn from player (Players.cpp):
  All math is relative to player position. Player position is frame-relative.
  Blaster spawn position = player position + offsets. Works as-is.

Missile spawn from player (Players.cpp):
  Same pattern as blasters. Position derived from player. Works as-is.

Spaceship blaster spawn (Spaceships.cpp):
  Blasters spawned at spaceship position. Both frame-relative. Works as-is.


================================================================================
5. RENDER MERGE (MergeFramesForRender) [REQUIRES NEW INFRASTRUCTURE]
================================================================================

NOTE: MergeFramesForRender and OffsetPositions do not yet exist. Currently
rendering operates directly from rRenderInterpolates. This infrastructure must
be built as a prerequisite.

Design:
  After this change, positions are frame-relative and need conversion to
  camera-frame-relative space during merge.

  Compute vecOffset per frame as:
      frame.vecOffset = frame.vecFrameOrigin - cameraFrame.vecFrameOrigin

  Camera frame gets vecOffset = (0, 0, 0, 0) (it IS the reference frame).
  Adjacent frames get vecOffset = their world origin minus camera's world origin.

  An OffsetPositions() function adds vecOffset to every position in each merged
  collection.

  Result: all merged positions are in camera-frame-relative space. Since the
  camera is in its own frame, camera-relative coordinates are small floats with
  full precision.

6. AUDIO
================================================================================

Two audio position paths exist:

A. PlayOneShot3d (one-shot sounds during PostRender):
   Signature: AudioManager::PlayOneShot3d(const game::Frame& rFrame,
     common::crc_t audioCrc, FXMVECTOR vecPosition, float fVolume, ...)
   (Engine/Source/Audio/AudioManager.h ~line 35, impl AudioManager.cpp ~line 558)

   Call sites with positions:
     - Players/PlayersUpdate.cpp (~line 474, 521) - shield/armor hit sounds
     - Missiles/Missiles.cpp (~line 533) - explosion sounds
     - Blasters/BlastersUpdate.cpp (~line 318) - terrain impact
     - Spaceships/SpaceshipsUpdate.cpp (~line 96, 401) - death/hit sounds

   Uses X3DAudio which computes RELATIVE emitter-to-listener distance.
   Listener position is set from player[0] position in the SAME frame.
   One-shot sounds from the CAMERA frame: both emitter and listener are in the
   same frame-relative space. Distances correct. No conversion needed.
   One-shot sounds from OTHER frames: emitter is in a different frame-relative
   space than the listener. Must convert emitter position to camera-frame-
   relative space:
     cameraLocalPos = localPos + (thisFrameOrigin - cameraOrigin)

   Sounds from non-camera frames are rare and far away (>500 units from camera).
   Still worth doing for correctness.

B. Persistent Sounds (Sounds collection via Sync pattern):
   Positions are synced from owner collections (missiles, etc.) during
   Interpolate::Update. After MergeFramesForRender (once built), the merged
   Sounds collection has camera-frame-relative positions (via OffsetPositions).
   AudioManager::Update reads from the merged frame. Listener is set from
   merged player[0] position. Both are camera-frame-relative. Correct.


================================================================================
7. CROSS-COLLECTION POSITION REFERENCES (NO CHANGES)
================================================================================

All cross-collection position comparisons operate WITHIN a single frame.
Since all positions in the same frame share the same coordinate space, these
need NO conversion:

  - Missiles -> Targets homing guidance
    Both in same frame. Direction/distance computation unchanged.

  - Spaceships -> Players nearest target
    Both in same frame. Distance computation unchanged.

  - Spaceships -> Targets sync
    Spaceship position synced to its owned target. Same frame.

  - Collision layers (PreCollision/PostCollision)
    All objects in same frame. Zone grid uses frame-relative bounds.

  - Pushers zone setup
    Centers arena on player position (frame-relative). All pushers in same
    frame also frame-relative. Zone mapping unchanged.

  - FrameInterpolateBase::IsVisible() (FrameBase.h)
    Compares two positions within same frame. Delta unchanged.

  - GetMissileTarget (Frame.cpp)
    All within single frame. Distances and angles unchanged.


================================================================================
8. POSITION INTEGRATION AND VELOCITY (NO CHANGES)
================================================================================

Movement integration (position += velocity * dt) works identically in any
coordinate space. Velocities are direction * speed, frame-independent.
No conversion needed for:
  - SpaceshipsInterpolate::Update (position += velocity * dt)
  - MissilesInterpolate::Update (position += velocity * dt)
  - BlastersInterpolate::Update (position += velocity * dt)
  - PlayersInterpolate::Update (position += velocity * dt)
  - All direction vector computations


================================================================================
9. RENDERING PIPELINE (NO CHANGES BEYOND MERGE)
================================================================================

After MergeFramesForRender converts positions to camera-frame-relative:
  - Visibility culling (IsPointVisible, InVisibleArea): camera is at its own
    frame-relative position, objects are offset to that space. Correct.
  - ProjectToBaseHeight (Engine/Source/Graphics/GraphicsUtils.cpp ~line 82-86):
    Queries terrain elevation via GlobalElevation. This happens during Render,
    AFTER merge. Positions are camera-frame-relative but terrain queries need
    world-space. Either:
      (a) Convert camera-frame-relative to world before terrain query
      (b) Pre-compute projected heights during PostRender (in frame-relative
          coords with world conversion) and store in the Interpolate struct
    Option (a) is simpler. The camera frame's vecFrameOrigin must be accessible
    during rendering for this conversion.
  - GPU buffer writes: shaders receive positions. As long as all positions are
    in the same coordinate space (camera-frame-relative after merge), rendering
    is correct. No shader changes needed.


================================================================================
10. SERIALIZATION AND REPLAY (NO CHANGES)
================================================================================

Positions are serialized as raw floats. Frame-relative positions are just
smaller floats. CRC, Write, Read, equality comparisons all work identically.
Replay compatibility will break (save file version bump needed) because
position values change meaning.
