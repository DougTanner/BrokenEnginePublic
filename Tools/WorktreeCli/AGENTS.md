# WorktreeCli

Standalone Windows console application for repository coordination. It owns serialized MSBuild invocation, landing leases, and the Git-backed `Documents/Plans` scheduler. It never connects to a game endpoint or owns the AgentHarness lock.

## Executable and Commands

Use `Tools\WorktreeCli\Platforms\VisualStudio2026\Output\WorktreeCli.exe` through the provisioned primary Output link. Routine linked-worktree workflows do not build or modify that output; wrapper session start incremental-rebuilds it in the primary so it tracks primary HEAD, and source changes use the `/compile` [candidate/promotion path](../../.agents/skills/compile/SKILL.md#full-build-commands).

- `lock token|claim|status|refresh|recover|release|steal` operates on landing locks identified by `--repo`. Lease state, not a record of which process took the claim, determines whether a lock is still held. A lease is lock ownership with a time limit that expires on its own if it is not renewed or released. `claim` accepts a bounded blocking wait (`--wait-seconds`, `--poll-milliseconds`) and recovers an expired lease internally during that wait, only while no registered worktree has a Git operation in progress. Lock responses report lease identity, timing, and validation state only, never private record fields such as the process id that took the claim, so no caller can start reading a process id as proof the lock is still alive. The stored record must still carry that process id in range to validate; a lease record missing it reads as unverifiable and fails closed. The shared store can hold other lock domains, but this surface stays repository-only: do not add a `--domain` option or harness-key support.
- `plan validate|list|claim-next|claim-status|unclaim|complete|reject` is the only scheduler surface. It reads tracked `Documents/Plans` metadata, uses deterministic `(createdUtc,path)` selection, and stores only short-lived machine-local claim records. `validate` lints metadata and reports quarantines, stale dependency edges, and healed claims; it evaluates no baseline and compares no metadata across commits. `list` previews the same decision `claim-next` would make without changing anything: it takes no scheduler guard, heals nothing, creates no storage, and reports every executable Plan of the session tree in `(createdUtc,path)` order as `eligible`, `blocked` naming its unmet prerequisites, `quarantined` with its diagnostic, or `claimed` with the live claim's session, worktree, and expiry; documents whose metadata never parsed stay in the diagnostics instead of becoming rows, and a claim record it cannot use is ignored rather than deleted. `claim-next` requires session `HEAD` to be an ancestor of (or equal to) the primary tip, evaluates eligibility, dependency blocking, and healing against the primary tip so a behind session never heals a peer's claim or claims past a prerequisite landed after its baseline, and reads the exact bytes the selector uses from the session tree. `complete` and `reject` rewrite the markers of direct dependency children, delete the target Plan file, and report every changed path; `reject` additionally requires `--user-authorized-rejection`.
- `build` prints one `broken-engine-build-result/v1` JSON object to stdout; human progress goes to stderr. It retains the combined MSBuild stream in the invoking worktree's ignored `Temp\AgentBuildLogs\` path and parses structured diagnostics from that same stream.
- Exit code `0` is success, `2` is a state conflict or negative result, and `1` is usage, transport, or OS failure. A build whose MSBuild step succeeded but whose retained log came out incomplete still exits `1`, with `retainedLog.complete` false, because the JSON result is only trustworthy when the log behind it is whole.

`BROKEN_ENGINE_MSBUILD_PATH` pins discovery and fails when invalid. `BROKEN_ENGINE_BUILD_LOCK_WAIT_SECONDS` may only shorten the standard 660-second lock wait and exists for fixtures.

## Coordination State

Landing locks and scheduler claims live under `%LOCALAPPDATA%\BrokenEngineLocks`. Scheduler claims are keyed by Git common directory and expire after 48 hours; invalid, expired, and orphaned local records self-heal. `Documents/Features` and `Documents/Investigations` are not scheduled.

Missing dependency paths are satisfied with a stale-edge notice. Invalid metadata and dependency cycles quarantine only their affected Plans component; unrelated valid plans remain claimable.

Executable markers contain exactly `createdUtc` and `dependsOn`; timestamps use canonical millisecond UTC (`yyyy-MM-ddTHH:mm:ss.fffZ`). Every tracked `Documents/Plans` document carries one at byte zero; an absent marker — including one displaced by a BOM — reports `invalid-metadata` naming the path. `AGENTS.md` and `CLAUDE.md` are exempt at any depth.

A claim records the Plan path, its owner, session, worktree, and branch, and its claim and expiry timestamps. It stores no baseline commit, digest, or lifecycle state, so a session that rebases or advances keeps the claim it holds. Healing deletes a record only when it is unreadable, schema-invalid, stored under the wrong claim filename, expired, bound to a worktree path that no longer resolves, or bound to a Plan that is absent or invalid at the primary tip — the last rule is what lets landing delete its own claim best-effort and heal a missed delete later.

Enumeration skips unreadable, schema-invalid, and expired claim records instead of failing on them; only a directory-scan error aborts the operation. Recovery removes only the diagnosed `.lock` file. Every scheduler change runs under the scheduler guard — a lock it must acquire first, so only one change touches scheduler state at a time — and fails closed: final operations clean only the hidden ordinary files stored next to the Plan file and updated atomically, and only those matching the exact Plan-owned temporary filename shape, and stop with a state conflict when a dependency child carries invalid metadata or the target file exists untracked. Never broadly delete coordination state.

## Project Ownership

Keep source membership synchronized between `WorktreeCli.vcxproj` and `.filters`. Shared Windows and coordination code belongs in `Tools/ToolCommon` and is compiled into both tools. Transient operation claims around shared-tool consumption use `.agents/scripts/WorktreeCliSessionExclusion.psm1`; bootstrap incremental-rebuilds the WorktreeCli, AgentHarness, and ThirdParty primary outputs at every session start, and best-effort prebuilds DataPacker Release so new worktrees seed it by verified copy.
